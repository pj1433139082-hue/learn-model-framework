# 数据源显式分流防偷懒门禁与双速运行架构

状态：已接受（2026-10-12）

## 背景

在模型研发与工程落地实践中，暴露出两个高频发生的关键痛点：
1. **智能体/开发者“偷懒”绕过真实 IoT 数据（防偷懒机制缺失）**：
   在点位模式（`serving.mode: point-code`）或算法验证时，由于真实现场数采需要配置厂站编码、账号凭据以及网络接口，开发者或 AI 智能体极易出现“偷懒绕过”的习惯性倾向——直接在工作区读取现成离线 `.csv`/`.xlsx`，甚至私自内嵌基准数据假装是在线数据。这导致离线指标看似完美，到了线上部署和容器回放时，因为点位映射不通、时间戳时区漂移、聚合逻辑不符或者网络网关权限缺失而直接翻车。
2. **强制唤醒 Linux 验证导致日常开发极慢**：
   此前为了防范 Windows 与生产 Linux 容器的兼容性差异（尤其是私有 `.so` 动态库与大小写敏感），框架将 WSL Linux 验证作为重要卡点。然而，日常算法迭代（改公式、调参数、跑私有单测）如果在每一步都唤醒 WSL、跨盘挂载和重型依赖预检，会造成开发体验极其沉重。用户需要清晰了解“为什么用 Linux”并拥有“不用 Linux 极速开发”的自主选择权。
3. **交互档位与确认问题缺乏立体分级映射**：
   此前交互档位（全自动、半自动、逐步确认）与问题级别（`AUTO`/`ASK`/`CONFIRM`/`AUTHORIZE`）虽然已存在，但在生命周期全景中未形成直观的二维正交对照表，容易导致“仔细提问”时颗粒度混乱或“全自动”时误越关键门禁。

## 决策

1. **确立数据获取策略双轨分流与防偷懒硬门禁（Anti-Cheating Gate）**：
   - **显式单选（`data_source_mode`）**：在 Stage 1 契约设计阶段，设立必填决策项 `requirements-data-source`（阻塞 `specified`，`level: CONFIRM`），强制选择且禁止隐式默认：
     - **选项 A：现场动态拉取（`live-iot`）**：基于厂站编码（`factory_code`）、账号凭据和点位编码列表（`input-bindings.yaml`），调用集团 IoT 数据接口进行真实时间窗口数据拉取；
     - **选项 B：离线基准文件（`static-baseline`）**：使用经业务确认的本地样本文件，但必须登记降级原因并打上 `offline-only` 标签，禁止无凭证直接发布上线；
   - **IoT 拉取回执（Pull Receipt）凭证法**：
     - 在 `live-iot` 模式下，数据拉取必须生成机器可信回执文件 `iot-pull-receipt.json`（记录时间戳、厂站编码、点位列表哈希、拉取条数和响应摘要）；
     - **release-gate 硬性拦截**：声明为 `live-iot` 的模型，若工作区内存在未在清单注册的本地私有表格文件，或代码/测试直接硬编码读取未经声明的本地表格，发布门禁直接判 **FAIL** 阻断推进。

2. **落地双速运行架构（Dual-Speed Runtime Architecture：极速 Windows vs 保真 Linux）**：
   - **日常研发极速模式（Stage 0~2，Windows Local Only）**：
     - 日常逻辑编写、参数调试、单测与离线指标回放 100% 在 Windows 本地 Python 3.11 运行（耗时 `< 0.1` 秒），**完全不唤醒 WSL、不调 Linux、不跑重型实包打包**；
     - 即使未安装 WSL 或不启动 WSL 的环境，也可畅行无阻完成开发并推进至 `validated`；
   - **生产发布保真质检（Stage 3~5，On-Demand Target Preflight）**：
     - 明确 Linux 存在的目标仅为“生产保真质检”（验证 Linux x86_64 容器、私有 `.so` 加载与路径严格敏感性）；
     - 仅在最终生成实包（`bundle-build`）及正式发布（`publish`）前，提供显式选项 `target_runtime_preflight: linux-wsl | skip-local-preflight`；
     - 若用户选择跳过 Linux 预检，框架在发布元数据中诚实标注 `runtime_audit: { verified_platform: "windows-dev-only", linux_container_preflight: "skipped" }`，允许降级生成制品并提示云端预发环境验证。

3. **固化交互档位与决策分级的二维正交矩阵**：
   - 将“交互档位（全自动 / 半自动 / 逐步确认）”与“决策级别（`AUTO` 事实级 / `ASK` 信息级 / `CONFIRM` 决策级 / `AUTHORIZE` 事务级）”在规程中建立结构化映射，明确每种组合下的暂停行为与门禁卡点。

## 影响

- **收益**：
  - 彻底铲除算法开发“偷懒假冒在线数据”的灰色地带，真实数采与离线降级边界清晰、追溯完整；
  - 日常开发速度提升数十倍，毫秒级响应，彻底消除轻量改动被 Linux 重型卡点拖累的沉重感；
  - 开发者拥有充分的选择权，既能极速开发，又能在临发布时按需获得生产级的保真守护。
- **约束**：
  - 声明为 `live-iot` 的模型必须持有有效取数回执才能发布，严禁混用未经申报的本地文件。
