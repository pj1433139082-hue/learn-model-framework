## 一、测试边界

- 使用一个全新 Clone，或由负责人提供的无业务修改副本。
- 只使用 Python 3.11；发现 3.12 时立即判定失败，不能自行降级或绕过。
- 不读取账号密钥，不连接集团 MLflow，不执行 `deploy_*.py`，不上传任何内容。
- 测试模型只能创建在临时目录；不得修改在役模型或其发布快照。
- 公司 311 部署能力是外部前置条件。缺失时应得到清楚提示，但不阻止控制面测试。
- 项目技能只从 `.skillshare/skills/` 同步到仓库内 `.agents/skills/`；不得创建或依赖 `superpowers`。
- 完整 `test-profile local` 需要仓库 Git 历史和 `.[test]` 依赖；纯文件副本只能验收安装、体检和新手基础路线，不能把全库档写成通过。

## 二、自动化基线

负责人先在仓库根目录执行：

```powershell
.\.venv-311\Scripts\python.exe -m unittest `
  tests.test_repository_doctor `
  tests.test_beginner_flow `
  tests.test_repository_layout -v
```

通过标准：环境体检、预览创建、显式创建和状态查看全部通过，并且测试不会访问
网络或写入远端平台。

## 三、新手人工路线

测试者依次完成以下任务，并记录自己实际看到的结果：

1. 打开 `docs/00-入口层/00-模型开发总览.md`，找到“人工操作快速开始”。
2. 按快速开始预览并执行 `skillshare sync`，确认七个项目技能（5 个场景技能 + `model-lab-setup` + `model-lab-router`）只进入
   本仓库 `.agents/skills/`。随后由真实 Codex 客户端使用者重新打开一个任务，
   核对技能是否自动加载；子智能体不能代替这项客户端人工检查，应报告“未验证”，
   不得把文件同步成功说成动态加载成功。
3. 按快速开始创建 `.venv-311` 并安装本仓库。
4. 运行：

   ```powershell
   .\.venv-311\Scripts\python.exe --version
   .\.venv-311\Scripts\python.exe -m model_lab doctor .
   ```

5. 确认版本是 `Python 3.11.x`，环境体检显示 `READY`。
6. 复制执行下面的命令，在系统临时目录预览一个 CPU/IoT 模型；预览后工作区
   不能存在：

   ```powershell
   $testRoot = Join-Path ([System.IO.Path]::GetTempPath()) `
     ("model-lab-novice-" + [guid]::NewGuid().ToString("N"))
   .\.venv-311\Scripts\python.exe -m model_lab new novice-cpu-iot `
     --name "新手验收模型" `
     --owner novice-tester `
     --target cpu-iot `
     --models-root $testRoot
   ```

7. 在同一条 `& .\scripts\model-lab.ps1 new` 命令末尾追加 `--apply`，确认只在 `$testRoot` 下生成
   统一的 `model.yaml`、`decisions.yaml`、Notebook、测试、运行环境
   说明和依赖锁。
8. 执行下面的命令查看状态，确认状态为 `draft`，并分别列出 `Open questions`
   与 `Pending confirmations`：

   ```powershell
   .\.venv-311\Scripts\python.exe -m model_lab status `
     (Join-Path $testRoot "_drafts\novice-cpu-iot")
   ```

   Windows 本机测试 Linux 目标且只有主机平台不匹配时，可能显示
   `Current build host: ADVISORY`；空白测点工作区缺少运行时取数信息时也可能显示
   `Runtime environment: BLOCK`。以具体 issues 判断缺项；平台提示本身不阻止
   需求和模型设计，真正构建部署包必须转到清单声明的目标平台。
   新建空工作区首行显示 `BLOCKED` 也属于预期结果，表示业务契约与规格尚未填写、
   暂时不能推进；只要 `Current state: draft` 且缺项清楚，就不是框架测试失败。
9. 打开生成的 `model.yaml`，确认 Python 为 `>=3.11,<3.12`；Notebook 元数据为
   `3.11`，且 Kernel 显示 `Python 3.11 (model-lab)`，没有 3.12 入口。
10. 在 Windows 本机先运行 `.\.venv-311\Scripts\python.exe -m model_lab test-profile --help`，确认能看懂 `local`（本机离线起点）、`linux-offline`（目标 Linux＋公司 ZIP）、`linux-online`（显式真实 IoT）和 `windows-network`（仅 Windows 主机网络诊断）；按人工快速开始先执行 `uv pip install --python .venv-311\Scripts\python.exe -e ".[test]"`，再运行 `.\.venv-311\Scripts\python.exe -m model_lab test-profile local`，核对末尾的 `next`。缺少测试依赖应在执行用例前报告 `BLOCKED`，不能把导入错误冒充模型失败。负责人持有经核验的公司 3.11 ZIP 时，在 Linux 3.11 的项目 Python 环境也安装 `.[test]` 并运行 `python -m model_lab test-profile linux-offline`，只替换外部 IoT 请求，检查公司包、数组签名、本地构建与离线预测；无 ZIP 时该目标档应明确报告 `BLOCKED`，而不是假装通过。
11. 再按[测点模式从零示例](../00-入口层/05-数采测点模型从零示例.md)，用另一个临时模型 ID 预览并创建 `--serving-mode point-code`；确认新增 `input-bindings.yaml` 2.1 骨架，时间策略、窗口、工厂和测点仍待填写。实际填点时要分别记录设施、设备、`point_id`、`signal_code` 与应有信号，并由 `model-lab validate` 检查完整编码的组合关系；不能把空模板误当成可发布模型，也不依赖本机 Git hook 才触发此检查。
12. 记录 `$testRoot` 的完整值并停止，不尝试真实发布；临时目录由负责人按精确路径
   核对后清理，不让新手执行宽泛删除命令。

## 四、子智能体测试提示词

每次大版本升级后，应新建一个没有对话上下文的子智能体，使用以下任务说明：

> 你是一名第一次接触本项目、不了解编程的普通同事。不要读取任何历史对话，
> 只从 `docs/00-入口层/00-模型开发总览.md` 开始。按照文档从零完成 Python 3.11
> 环境体检、项目技能识别、预览创建一个 CPU/IoT 模型、显式创建到临时目录、
> 查看开放问题和确认门禁。禁止访问
> 远端平台、运行旧 deploy 脚本或修改在役模型。逐步记录：是否知道下一步、命令
> 是否能复制运行、结果是否看得懂、哪里容易误操作。最后按“通过/阻塞/文档歧义”
> 分类报告，不替开发者修文件。

推荐验收模型为 GPT-6 Luna Max，并使用全新上下文启动。

## 五、判定标准

以下条件必须全部成立：

- 测试者不依赖口头补充就能从入口层找到完整路线；
- 项目解释器、模板、Notebook 和新工作区全部是 Python 3.11；
- 3.12 legacy Profile 不能通过 `& .\scripts\model-lab.ps1 new` 选择；
- 缺少公司部署能力时，提示明确说明“不要回退到 3.12”；
- 预览不写文件，`--apply` 只写指定临时模型工作区；
- `status` 不执行模型源码、不访问网络；
- `status` 能区分待回答问题和待确认决定，开放的必填决定会阻塞 `advance`；
- 测点模式从统一入口可发现、生成绑定骨架，且有可复现的 Python 3.11 离线构建和推理测试；缺少公司 ZIP 时给出真实依赖缺口；
- 长对话续办能从文件与门禁恢复任务事实；测试结果说明当前验收边界和下一步，只有未解决的业务选择才要求人工确认；
- 没有改动在役模型、15 个历史发布快照或远端平台。

### 问答分流与选档验收

框架交互变更还要用一个**没有历史对话**的新任务，依次给测试者以下六种
自然语言意图。每次记录智能体实际展示的问题、选择与停点，不能仅凭技能
文件存在就判定客户端行为通过：

| 意图 | 预期交互 |
|---|---|
| “这个模型为什么报错？只查” | 直接只读调查，不弹交互档位或新模型问卷 |
| “从零做一个模型” | 首次回复展示三档，用户可选；随后只问当前缺失的用途、契约和验收口径 |
| “把已发布模型迁到 3.11，行为不变” | 只核父版签名与基线；不重复问旧公式和已证实的字段 |
| “把数值输入改成测点数组” | 按契约升级分叉，只问变化的点位、窗口和验收，不伪装成补丁 |
| “看看数据质量/把测试跑完” | 自动计算统计与指标；只有处理取舍或验收偏差才集中提问 |
| “上传这个模型，编号和账号已给” | 不重问编号、账号或形式化上传授权；先查同版本逐 Run 回执，已有 Run 但缺机器回执则只读复核原 Run；确无 Run 且固定实包验收通过时按限定指令发布，不推定允许生产调度 |

还应单独模拟一个“构建和测试已经完成、`status` 显示必填验证结论或发布处置
决定待确认”的续办请求。智能体必须先展示本轮独立问题的编号、推荐答案及
其他答法；先记录可见文字选项，再发送客户端支持的结构化选项。另模拟一次
“工具返回已发送/accepted，但使用者未看到控件或没有回复”的情况；工具回执
不能算使用者已看见或已同意。若没有收到答复，最终交接
必须重述问题；收到“全部按推荐”时仅关闭**本轮已展示**的决定，保存完整
答案，重跑 `status`，无需再为写文件和本地状态推进单独请求许可。记录实际
可见消息与工具调用的先后顺序、控件是否由使用者看见、文字答复能否完成同一
决定；只看工具 accepted 回执、技能文件或子智能体文字输出不算桌面
交互验收。

对每个可写场景分别选择一次 `full-auto`、`assisted`、`manual-review`，
观察只改变本地停点、不改变 `decisions.yaml` 必填门禁。用户回复“全部按推荐”
时，仅本轮已展示的独立问题获答；续办同一任务不再选档或重复问已记录答案。
若 Codex 客户端的选项交互未实际试验，应报告“文档/技能源校验通过，客户端
交互未验证”，不能写成端到端通过。

任一条件失败，框架升级不得标记为可交付。测试报告必须附完整命令、退出码、
关键输出和发生歧义的文档位置。

### 测点版发布前计划验收

若已有经过 Linux 3.11 验证的测点版实包，在只读 `& .\scripts\model-lab.ps1 dry-run` 中还要
核对两层输入：`inputs` 是取数后给算法的数值特征，`platform_inputs` 才是
实际 `MLmodel` 请求签名，测点字段须显示为 `Array(string)`。使用者应能从
输出中判断平台要填写测点编码数组，而不是数值。实包目录摘要与清单不一致
必须阻断计划；同一清单和实包移到不同 Clone 目录后，`plan_id` 不应变化。
即使这些检查通过，也不得把只读计划说成平台上传、Run 或在线推理回执。
