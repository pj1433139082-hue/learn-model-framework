# GPU 目标的显式授权上传通道

状态：已接受（2026-10-14）

## 背景与决定

[ADR 0016](0016-固定实包发布替代全局禁用.md) 的 `publish` 适配器只覆盖"具备在线验收收据的
CPU-IoT 测点模型"，GPU 目标在框架内没有上传通道；[ADR 0034](0034-GPU目标的离线发布适配器与跨操作系统服务包.md)
也把远端上传列为非目标。内网打通后（Hillstone `VirtualNet` 的 PMTUD 黑洞已定位并修复）
平台侧确认可用，用户授权参照公司 GPU 包推进上传。本 ADR 记录由此引入的上传通道及其边界。

1. **上传与打包分离，且上传必须双重显式。** `gpu-publish` 默认只读预览；真正写入需要
   `--apply` **与** `--authorize-publish` 同时出现，缺一即报 `missing_publish_authorization`。
   单一 `--apply` 不足以表达"向公司环境写入"这一动作，而
   [ADR 0004](0004-发布必须显式授权且默认只读.md) 要求发布是显式授权事务。
2. **凭据只从环境变量读取。** 只认 `MLFLOW_TRACKING_URI`、`MLFLOW_S3_ENDPOINT_URL`、
   `AWS_ACCESS_KEY_ID`、`AWS_SECRET_ACCESS_KEY`。框架**不实现**读取公司包内嵌混淆凭据的代码路径：
   那段载荷的密钥与密文在同一个文件里，任何拿到文件的人都能还原，
   [ADR 0002](0002-部署能力包不得携带长期凭据.md) 已判定部署能力包不得携带长期凭据。
   框架只报告变量名与缺失项，从不读取或打印值，回执里也不写。
3. **非公司跟踪端点默认拒绝。** 跟踪端点主机不以 `bewg.net.cn` 结尾时报
   `foreign_tracking_endpoint`，除非显式设 `MODEL_LAB_GPU_ALLOW_FOREIGN_ENDPOINT=1`。
   模型制品可能携带厂站相关行为，误传到公共 MLflow 是数据边界事故，不是便利性问题。
4. **失败必须发生在任何写入之前。** 顺序固定为：解析模型并校验服务包 → 读凭据 → 端点守卫 →
   缺凭据即停 → 检查 `boto3` → 才生成或复用 `validation_results` → 上传。
   这样"失败"不会留下半份载荷，也不会先写了表格再报错。
5. **一次 run 记两棵制品树。** `mlflow.log_artifacts(<bundle>, artifact_path="service")` 与
   `mlflow.log_artifacts(<validation_results>, artifact_path="validation_results")`，
   `model_uri = runs:/<run_id>/service`。run tag 只打硬件事实
   （`author`、`device`、`cuda_version`、`torch_version`、`platform`、`publisher`），
   不打 `framework=chronos-forecasting` 与 `model_type=chronos2_gpu`——那两个描述的是公司工具的
   Chronos 模板，套到别的模型上是错误标注。
6. **上传成功要留回执。** 在工作区之外的载荷目录写 `publish-receipt.json`（模型 id、bundle 摘要、
   run id、`model_uri`、端点、tag、时间戳），不含任何凭据。
   [ADR 0031](0031-发布回执判定的单一权威.md) 要求回执是判定的单一权威，本地也要有可核对的凭据。
7. **上传成功不等于契约已确认。** 报告固定附带"平台契约未确认"的说明；
   [GPU 平台发布契约确认清单](../10-流程层/22-GPU平台发布契约确认清单.md) 的 Q1
   （没有 `customize_service.py` 的包能否被 `ai-serving-gpu` 加载）未答复前，
   不得把"上传成功"写成"可服务"或"已上线"。

非目标：GPU 在线验收（[ADR 0016](0016-固定实包发布替代全局禁用.md) 不变）；
不读取公司包内嵌凭据；不自动创建 S3 bucket。

## 后果

- GPU 目标现在有完整的本地→远端链路，但每一步都需要人明确说"做"：预览永远安全，
  上传要两个开关同时给，凭据要从环境里来。
- `boto3` 成为控制面上传的前置依赖（本机 `.venv-311` 当前未安装，缺它时报 `missing_s3_client`）。
  这属于控制面环境，不进 `runtime/requirements.lock.txt`——后者是模型运行期锁。
- `gpu-publish-plan` 的说明文字与 `publisher` tag 随之更新（`model-lab gpu-publish`），
  两条既有测试改为断言新语义：计划命令**不再**声称"上传不可能"，而是必须点名未确认的契约
  与真正阻塞上传的那个问题。
- 上传成功的证据强度是明确的：只证明平台接受了制品，不证明服务能起来。
- **首次真实上传（2026-10-14，经用户显式授权的一次性测试）**：run
  `2c0e2c50708346b1a124b78ec5f1100e`（实验 165），
  `model_uri = runs:/2c0e2c50708346b1a124b78ec5f1100e/service`。两棵制品树尺寸与本地包
  逐项一致，run tag 只含硬件事实。以 `mlflow.pyfunc.load_model` 从远端拉回该 run 后，
  8 行验证样本的预测与本地 `output_result.csv` 逐值一致——第 1 条决定的链路在真实环境成立，
  并顺带验证了 ADR 0034 第 5 条的跨操作系统修复。**Q1 仍未答复，故"可服务"结论仍不成立**，
  证据明细见 `docs/10-流程层/22-GPU平台发布契约确认清单.md` §1.5。
