## 一、路径祖先检查

### 已核实的结构

`environment.py`、`scaffolding.py` 和 `lifecycle.py` 分别遍历路径及祖先，检查链接或 Windows junction。多个调用者从 `scaffolding` 私有导入 `_refuse_symlink`；Python 3.11 的 Windows junction 判定已经在 `path_safety.py` 中。

这些调用者还有不同的政策：本机初始化检查本地磁盘与网络文件系统；外部工作区检查禁止在框架内写入；部分入口接受尚不存在的目标目录。不能因为祖先遍历类似，就把全部规则合成一个校验模式。

### 候选设计

只把有序路径祖先扫描放进现有 `path_safety` module，给调用者明确的公开 interface。路径规范化、允许的目标类型、外部目录政策和错误分类仍归调用者。保留各写入入口的检查，不因集中复用就减少检查次数。

不得先调用 `resolve()` 再检查，从而隐藏经过链接或 junction 的原始路径。须覆盖 `..`、相对路径、尚不存在的末端、框架目录及祖先链接；不声称此次改造消除了全部文件系统竞争条件。

### 验收要求

通过公开 `model-lab` 写入入口确认拒绝违规路径且未创建或改变工作区；现有 Python 3.11 junction 兼容测试继续保留。Windows 实际 symlink/junction 检查和 Linux 检查分别报告，权限不足的跳过不能记作已通过。

## 二、受限 ZIP 读取

### 已核实的结构

`repository_doctor.py` 的外部能力检查和 `provider_archive.py` 的构建读取都限制 ZIP 总大小为 16 MiB、所读取成员大小为 2 MiB，并拒绝重复成员和缺失的必要成员。

两者验证强度不同。doctor 做静态文件和目标平台格式检查，不执行公司代码，也不证明真实网络可用；构建读取额外核对整包与必要成员的固定 SHA256，并验证 Linux 原生运行时格式。doctor 的 `files_verified` 不能被解释成已通过构建或部署验收。

路径政策也不同：doctor 要求 ZIP 在框架外且路径祖先无链接；provider 读取目前只检查末端常规文件和链接。共享读取不能无意增加或删除这些调用者政策。doctor 保留 Windows `.pyd` 与 Linux `.so` 分支，构建保留当前 Linux-only 契约；公司能力未配置不等于通用框架不可用。

### 候选设计

共享的 module 只负责有界读取 ZIP 与指定成员，不创建目录、不解压成员、不导入代码、不访问网络。调用者继续拥有路径政策、摘要固定、目标平台检查和结果分类。

不能让 doctor 的较弱检查成为构建默认政策；不能因为共享接口就丢失成员重复检测、大小限制或读取失败的明确结果。共享读取应统一观察同一份已读取内容，避免摘要校验与解析针对不同文件快照。

PowerShell/Bash bootstrap 仍是平台 adapter：首次初始化时 Python 可能尚不存在，不能强迫它先调用尚不可用的 Python 检查。

### 验收要求

使用虚构 ZIP 经公开 doctor 与构建入口验证正常、重复成员（包括无关成员）、必要成员缺失、目录成员、超限、损坏、整包摘要不匹配、成员摘要不匹配及目标原生格式不匹配。确认无解压、无执行和无联网；不依赖实际公司 ZIP 作为测试资料。

关键差异用例：相同的结构正确 ZIP，在模型固定摘要错误时 doctor 仍可报告文件已检查，构建必须拒绝；Windows 合成包只在 doctor 对应目标下通过。构建预览入口可以检查合成 ZIP 而不导入 MLflow。当前测试缺少成功的 provider/`bundle-build` 读取与这些差异的覆盖，需要新增而不能只依赖现有 doctor 测试。

## 三、操作完成与本地记录恢复

### 合成实测

子智能体使用本仓库 Python 3.11.15，在 TEMP 的虚构外部目录执行公开 CLI。只将索引写入 seam 注入 `OSError`：

1. `new --apply --format json` 已创建唯一的 `model.yaml`，状态为 `draft`，但未创建状态索引。
2. 命令退出码为 2，stderr 说明创建成功但索引失败，stdout 为空，无法作为 JSON 解析。
3. 随后 `context --write --format json` 返回 0，`valid: true`，索引同步；原清单字节不变，仍只有一份清单，生命周期未推进。

上述是合成故障恢复证据，不是实际模型部署验收。未访问公司网络或连接 MLflow。

### 发布路径的静态核对

`publish_fixed_bundle` 在指定远端 Run 已核验后，本地回执或索引失败时保留 `published / verified_local_record_incomplete`。

`verify_existing_publication` 在远端已核验后写入本地记录；索引失败会落入外层异常处理，返回 `blocked / verification_error`，阶段为 `local-record`。这与上传入口的分类不一致，而且此时本地回执可能已写入。

已存在的清单原子写入、并发保护和索引原子替换需要保留；不以新的统一提交模块替代它们，不把清单与派生索引伪装成一个跨文件或跨远端事务。

### 候选恢复原则

- 操作前的校验失败、事实提交失败、Run 不匹配或预测核验失败继续阻断。
- 已核实完成的事实与本地记录不完整分别报告，不因后者否定前者，也不把未经核验的远端行为说成成功。
- 索引可重建，不回滚已完成的创建、状态推进或远端 Run。
- 缺索引使用 `context --write`；缺发布回执须对同一 Run 重新核验并恢复记录，不能仅靠生成索引伪造回执。
- 恢复前仍执行路径、模型事实和并发校验。禁止在恢复中重新创建、推进、上传、删除回执或切换版本。

### 已确认 Q1：是否自动补写

采用：只对已具备完整事实、可安全重建的索引补写一次；仍失败则报告记录不完整和下一步。没有完整事实、不安全路径或校验失败不得重试或绕过检查。

备选：不自动补写，直接报告并给手工恢复命令。

### 已确认 Q2：输出兼容策略

采用：中文说明和可解析 JSON 同时表达操作结果、记录结果、是否可重做与恢复下一步。正常成功输出保持兼容；未恢复的本地记录失败仍保留非零退出码，并明确不能按该退出码重复操作。

备选：只补充中文说明，JSON 不变。

具体字段名和枚举在确认后的规格中固定；实现完成前不能将规格写成已经交付的接口。

### 验收要求

通过公开 CLI 验证创建、维护分叉、草稿分叉和状态推进的“事实已完成、索引失败”结果及后续安全恢复；通过发布/核验的公开 interface，用外部系统测试替身检查已核验 Run 后本地记录失败的分类。

分别注入可恢复的一次故障、持续写入故障，以及事实写入前失败；验证可解析输出、退出码、无重复工作区、无重复推进、无额外 Run 或远端写入。检查危险路径和并发变化仍被拒绝。
