# 11-新模型开发 SOP（v2）

> 原则：**先理解、后文档、再数据、最后代码**。每步有明确产出物，缺了不让进下一步。
> 用户在部署前必须见过：理解文档 + 数据质量分析 + 结果可视化。

本文是九步执行清单，从属于入口层的六阶段：需求（①）、设计（②）、构建（③④⑦）、验证（⑤⑥）、发布（⑧）、运营（⑨与持续维护）。

## 公共入口与工作位置

- 新模型只通过 `model-lab new` 规划或实例化；不得复制历史 deploy 脚本模板（已移入归档分支）或任一在役模型目录充当起点。
- 新模型工作区固定在 `models/_drafts/<model-id>/`。`models/` 下现有八个在役模型保持原位，不迁移、不改名、不重新脚手架化。
- 每次继续工作先用 `model-lab status` 确认当前状态、下一准入门禁和缺失证据，再用 `model-lab advance` 申请推进；不得手工修改 `model.lifecycle_state`。
- 智能体通过 `model-lab-router` 做场景分流；先从资料与工具计算事实，只把当前无法推导、需要业务选择的决定集中成一轮询问，每项先给推荐。
- `new` 与 `advance` 默认只给计划，只有显式应用才允许本地写入。
- 用户明确交办单模型开发后，本地 `new --apply`、构建、测试和逐级 `advance --apply` 属于同一任务执行范围，不再逐步追问授权；每条命令仍显式 `--apply` 并接受机器门禁。Git 远端操作和真实发布需要明确限定目标与内容的指令，推送不自动包含合并。授权不写进 `decisions.yaml` 形成长期许可。
- 已验收 CPU-IoT 测点模型可由固定实包适配器执行真实上传；其他目标仍停在 releasable。不得以旧 deploy 脚本、Run ID 占位符或本地验证结果冒充 released。

上述三个命令是当前公共 Interface；旧命令仅用于兼容诊断。分流规则见 [`../00-入口层/03-模型任务分流与加载矩阵.md`](../00-入口层/03-模型任务分流与加载矩阵.md)。

## ① 需求理解与沟通（半天~1天）

- 先运行 `model-lab new` 查看模型脚手架计划；需求未说清前不加 `--apply`。

- 先从现有资料核实下列口径，只对无法推导或需业务拍板的项目集中询问：
  - 模型目的（算什么/给谁用/什么频率）
  - 输入：哪些测点、单位、口径（瞬时/累计/均值）
  - 输出：列名、类型、取值范围、业务含义
  - 公式来源与每个参数的含义（工艺经验值？设计值？可调？）
  - 边界与特例（死区、过滤线、无效数据怎么办）
- 发现数据测不到/量级矛盾 → 当场提出（如 Model 5：无缺氧池表→进水÷5 方案）
- 产出：沟通结论要点（供 ② 文档用）
- 同步产出：`decisions.yaml` 中当前 `ASK` 项的完整答案；不能只把回答留在聊天记录。

## ② 理解文档（部署前置，必出）

- 新模型先在工作区的 `model-spec.md` 固化；不要在草稿阶段改写共享规则目录：
  - 参数含义表（每个参数：符号/含义/单位/来源/默认值/是否可调）
  - 公式规则（每一步可执行 + 物理自检：量纲闭合、方向合理）
  - 测点清单（点位编号+信号名，台账核过）
  - 待确认项 → **智能体给出推荐，用户按轮次拍板**
- 冻结前不写部署代码；`CONFIRM` 的完整推荐、完整答案、确认人和带时区时间写入 `decisions.yaml`，业务理由写进文档。
- 用户回复“按推荐”时必须展开为已经展示的推荐内容，不能把“按推荐”作为最终答案保存。
- 产出：工作区 `model-spec.md` 的需求与设计段落。现有八个在役模型继续沿用各自在 `docs/90-归档/` 的参数确认记录与归档记录。

## ③ 数据拉取与参数可视化（必做）

- 使用经批准的公司取数接口按其真实上限分段拉数，尽量覆盖完整周期（≥7 天优先）。历史脚本里的 `fetch_iot_chunked` 是各脚本的本地函数，不是本框架统一 API；先按[公司 3.11 取数制品](./17-公司311取数制品.md)核对目标接口，不能直接复制旧脚本或把旧的 1500 条上限当成已验证的新版能力。缺少真实取数能力时保留数据审查门禁，不用模拟数据宣称审查通过。
- **所有取用参数逐条出图**（时序线图，标注单位）
- 产出：参数时序图集（进 `plots/` 或 notebook 内嵌）

## ④ 数据质量分析（必做）

- **缺失值**：每列缺失率、连续缺失段、判别"表坏/通信断/正常空值"
- **异常值**：量级是否物理合理（上下限）、跳变（累计表回零/阶跃）、停滞（数据冻结表）、重复/恒值
- **工艺分段**：按 昼夜时段 / 工况（泵启停/进水高低负荷）/ 天/周 分段，**每段单独统计**，看数据行为是否随段变化（如 Model 5 昼夜节律）
- 处理规则（过滤阈值、去零、取均值）写**理由**存档
- 如果处理规则改变数据口径，必须确认 `build-data-quality-treatment` 决定后才能推进。
- 产出：数据质量结论 + 处理规则（写进 ② 文档的"实现约定"）

## ⑤ 模型分析与验证（必做）

- 规则/公式跑在干净数据上
- 在受控本地环境显式运行模型测试和 Notebook；`status` / `advance` 不执行草稿代码，只核对静态结构与验证记录
- **触发分布**：每个分支/档位有多少样本（三档全触发才健康；零触发=死逻辑要查）
- **物理自检**：结果范围/方向/量纲符合工艺直觉
- 对照：与真实值/经验值/均值对比（如 OTE 双口径互检）
- 产出：验证结论（数字 + 判断）以及复现命令、退出码和输出摘要

## ⑥ 输出可视化（必做）

- 结果出图：输出序列 + 阈值线/分区色带 + 状态标注（一张图看懂业务动作）
- 用户过目 → 确认后再进部署
- 结果确认写入 `validation-outcome` 决定；自动计算的指标和图表不需要用户重复计算。
- 产出：结果图（如 `rint_nh4_7d.png`）

## ⑦ notebook 固化

- 新模型工作区使用 `models/_drafts/<model-id>/` 下由脚手架声明的 Notebook 路径；现有八个在役模型继续沿用 `models/0X_<模型名>/ML-model-N_<名>.ipynb`。
- Notebook 内容顺序：首页通用说明 → 环境 → 测点 → 参数 → 拉数 → 数据处理 → 模型 → 输出可视化 → 结论
- 全自动跑通（nbclient 验证 OK_ALL）
- 产出：可复现 notebook

## ⑧ 发布准备与已支持模型的固定实包上传

- 先用 `model-lab status` 确认验证证据齐全，再用 `model-lab advance` 预览进入 releasable 的计划。
- 门禁通过后，显式应用本地状态推进。到达 validated / releasable 后，再显式运行只读 `model-lab dry-run <workspace>/model.yaml --format json`，生成确定性的计划 ID、目标适配器、制品摘要和发布前步骤。
- 仅具备已验收 CPU-IoT 测点适配器的模型可在 Linux Python 3.11 下执行 `model-lab publish --apply`；其他模型仍停在 releasable。任何失败都不得生成虚假 Run ID 或把工作区移入 released-only 的在役层。
- 发布界面沿用两项用户输入：平台实验名（模型编号）与发布作者标识（账号）；目标环境从 `model.yaml` 取得，环境、制品和依赖由框架核验。作者标识不是认证凭据；技术阻塞只报告一次，不反复索要授权。
- 各 `deploy_*.py` 只保留给现有八个模型做兼容审计，不是新模型模板，也不是发布授权；历史 deploy 脚本模板说明已移入归档分支。
- 产出：releasable 状态报告与只读 dry-run 计划；若该目标已支持且用户已给出限定上传指令，再执行固定实包上传并保存真实 Run、远端摘要和预测回执。网络不可达时保持 releasable，不另设公司审批门槛。
- 到达 releasable 后保存 `status` 返回的决定摘要 SHA-256；未来真实发布快照必须绑定该摘要。

## ⑨ 运营资料准备（真实发布后才生效）

- 理解文档先补“预期实现与部署记录”段；只有未来真实发布成功后才能写入 Run、实验和最终输出记录。
- **平台参数示例**先保存在模型工作区，以当前 MLflow 签名和测点绑定为准；评估目标仅在该模型的评估/配置界面确实需要时另填，不作为推理必填输入。
- MLflow 上传成功先保存逐 Run 回执，不因本地仍是 `releasable` 就重复上传；以后完成在役发布快照归档时，再按版本更新共享配置主档和模型归档记录。当前不把这两步写成自动原子操作。
- **部署说明**：平台输入字段/类型、测点编码、适用时间范围和执行方式；一次性手动不配置周期调度，实际定时任务才写调度频率。
- 产出：待发布交付包（模型 + JSON + 说明）；MLflow 上传不自动完成公司业务平台的任务配置，未验证的链路须单独说明。

## 交付物检查（当前检查到 releasable）

- [ ] 参数可视化（③）出图
- [ ] 数据质量结论（④）：缺失/异常/工艺分段记录
- [ ] 模型验证（⑤）：触发分布 + 物理自检数字
- [ ] 输出可视化（⑥）用户已过目
- [ ] notebook（⑦）全绿
- [ ] `status` 显示验证门禁通过，`advance` 的 releasable 计划无缺项
- [ ] 未执行远端上传，未生成虚假 Run ID，资产仍位于 `models/_drafts/`
- [ ] JSON（⑨）：已形成待发布草案；真实平台字段保持未发布语义
