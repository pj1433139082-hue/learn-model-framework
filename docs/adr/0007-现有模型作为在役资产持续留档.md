# 现有模型作为在役资产持续留档

状态：已接受（2026-09-16；状态行补记于 2026-10-10）

后续修订（2026-10-10）：“当前八个模型全部作为在役模型资产”这一口径由 [ADR 0020](./0020-历史审计证据由归档分支保存.md) 细化为三档发布状态——已验证发布（存在 `status: verified` 的机器回执）、仅历史记录（`deployment_status: finished` 但无回执）、归档未完成（`run_id` 与 `deployment_status` 均为 `pending-archive`）。八个模型仍全部作为在役资产长期保留、不降级，但中央资产目录必须区分三档，不得一律标为 `active`。

后续修订（2026-10-10，维护投入）：八个模型的维护投入已不再一致——业务上只有 04 上游来水水量实时测算与 05 分区曝气阀门排队启停逻辑仍在使用（平台当前生效的是它们的 V002 次版本），其余六个已停用。但清单的 `model.maintenance_status` 仍全为 `active`：维护草稿以父 `model.yaml` 的全文摘要钉住血缘，改动父清单任何字段都会被判为“父版在分叉后被改过”，涉及 12 个草稿、其中含一个已 validated 的实体工作区。因此停用事实先记录在本页、`models/README.md` 与模型开发总览，清单字段的改动需连同这些草稿的处置一起单独决策。本决策中“只有明确停止维护时才进入 retired”继续有效；`retired` 仍是不再分叉的终态，不用于将来可能改造后重新上传的模型，`unmaintained` 才是这种情形的维护状态取值。

后续修订（2026-10-10，血缘口径）：上一条记录的阻塞已解除。维护草稿的血缘摘要不再钉父清单全文，改为只钉决定子版本正确性的字段（契约、行为基线、目标、身份、版本、平台记录、制品登记），并显式排除 `model.maintenance_status` 与 `source` 段的三个引用路径字段；发布快照摘要采用同一口径。排除清单而非白名单，因此清单新增字段默认被钉住（失败封闭），放宽口径必须是一次显式改动并由测试逐叶子锁定。旧全文口径经 `model-lab repin-lineage` 一次性迁移：该命令只在草稿于**旧**口径下仍然有效（父清单与发布快照都一字未改）时才换算法，父版真变过的一律拒绝，避免迁移沦为伪造血缘证据的洗白通道；默认只预览，`--apply` 才写盘。迁移必须排在任何父清单改动之前：命令用**旧**口径核验父版未变，先改父版会让它拒绝迁移——本次落地时先改了六个 `maintenance_status` 再迁移，命令如实拒绝了那 12 个草稿、只迁移了父版未动的 4 个，随后按正确顺序重做才全部通过。据此六个停用模型的 `maintenance_status` 已改为 `unmaintained`，04 与 05 保持 `active`，16 个维护草稿血缘全部有效。上一条中“`retired` 仍是不再分叉的终态、`unmaintained` 才是这种情形的取值”继续有效。

后续修订（2026-10-12，状态命令输出对齐）：针对 #31 冷启动复测发现在役资产执行 `model-lab status` 提示 `Next state: retired` 易被误解为默认下一步的问题，已在 #35 对齐命令输出：在役 `released` 资产的下一步不再提示 `retired`（显示 `<none>`），并清除误导性的 `Decision scope: released -> retired`，输出明确解释指向本决策与 [ADR 0015](./0015-在役模型维护版必须安全分叉.md)，强调停用（`unmaintained`）不等于 `retired`，在役演进一律使用 `maintain` 创建草稿。

当前八个模型全部作为在役模型资产长期保留，而不是在新版体系中降级为一次性遗留占位。源码、Notebook、规则文档、资产清单和脱敏行为基线进入 Git 历史，模型制品与大型数据由受控制品服务保存并以摘要关联；后续修复产生新的模型发布版本和发布快照，旧版本及其行为基线继续可追溯，只有明确停止维护时才进入 retired。
