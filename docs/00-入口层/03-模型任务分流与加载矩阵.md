# 03-模型任务分流与加载矩阵

> **本仓是公开框架分发仓**：`step-check`、`ledger`、`.dsh-hooks` 属私有源仓的每步核对机制，本仓未提供；本仓请用 `model-lab status` / `model-lab context`，hook 用 `.codex/hooks.json`。下文保留私有源仓原文作为决策背景。

> 开局第一轮不需要本页：目标没定位时按 `AGENTS.md` 的开局三条只问一次「哪个模型 + 想做什么」，拿到答复再按 `& .\scripts\model-lab.ps1 context <工作区> --task <意图>` 取最小加载清单。本页服务的是“已经知道大概要做什么、要查清该走哪条路”的第二轮。
>
> 本页定义当前公共 Interface 与**唯一路由事实源**；`model-lab-router` 技能只是指向本页的指针，不另存一份路由长文。`inspect`、`validate` 属兼容诊断，`toolchain-drift` 只提供可见性（只报漂移、不成门禁），`dry-run`、`catalog` 和 `release-gate` 同为兼容诊断入口——它们都不与主流程并列，也不得被误用来手工创建模型工作区。`step-check` 是每步交付物的机器核对入口（见「任务分流」与调用示例）。`ledger` 是每步状态的登记与复核入口：`ledger set` 记录每步的声称与证据指针，`ledger check` 复核声称与重算的差异（0＝一致、1＝漂移），只作用于 `ledger` 子命令，不改 `step-check` 的退出码与门禁结论；台账里的 status 只是声称，判据仍由 `step-check` 重算。`ledger set/check` 也只在本文登记路由：本页仍是唯一路由事实源，技能只是指向本页的指针。符合 ADR 0016 的固定实包发布有窄范围适配器；预览仍只读。

## 唯一入口

使用者从 CLI 入口 `scripts/model-lab.ps1` 进入；新模型日常生命周期只需记住 `new/status/advance`，
已有模型用 `maintain/draft-fork`，`context` 辅助恢复版本上下文。下文命令都写成可直接执行的形式：pwsh 用 `& .\scripts\model-lab.ps1 X`，bash 或要接管道/`--format json` 时用 `.\.venv-311\Scripts\python.exe -m model_lab X`——裸写 `model-lab` 不在 PATH 上，会 CommandNotFound。

| 任务 | 公共入口 | 默认效果 | 允许的写入 |
|---|---|---|---|
| 初始化环境与配置 | `& .\scripts\model-lab.ps1 setup` | 检查仓库外私有模型根目录（`--models-root`）、依赖与本机设置 | 仅显式 `--apply` 后写入 `.model-lab.local.json` |
| 查看或记录任务计划卡 | `& .\scripts\model-lab.ps1 task-plan <工作区> --task-id <task-id>` | 读取任务交互档位与下一步动作 | 仅显式 `--apply` 后写入 `<工作区>/.model-lab/tasks/<task-id>.json` |
| 新建模型或登记待迁移模型 | `& .\scripts\model-lab.ps1 new` | 生成模型脚手架变更计划 | 仅显式 `--apply` 后创建 `models/_drafts/<model-id>/` |
| 已发布模型的行为不变补丁 | `& .\scripts\model-lab.ps1 maintain` | 核对父版本和新补丁版本，生成安全分叉计划 | 仅显式 `--apply` 后创建 `models/_drafts/<model-id>-<version>/`；父版本不变 |
| 已发布模型的测点数组与历史窗口契约升级 | `& .\scripts\model-lab.ps1 maintain --change-kind contract-upgrade` | 核对下一次版本、父版摘要与独立在线契约门禁 | 仅显式 `--apply` 后创建另一版本草稿；原补丁草稿和父版本不变 |
| 未发布数值草稿改为测点数组 | `& .\scripts\model-lab.ps1 draft-fork` | 核对父草稿 `releasable` 状态、冻结的源码与决定摘要及下一次版本；新版从 `draft` 重新走门禁 | 仅显式 `--apply` 后创建同 ID 的新版本草稿；原草稿和数值包不变 |
| 查看当前状态与下一步 | `& .\scripts\model-lab.ps1 status` | 校验模型资产清单，报告当前状态、缺失证据和下一准入门禁 | 无 |
| 查看版本上下文与最小资料 | `& .\scripts\model-lab.ps1 context <工作区>` | 从事实源现算本地阶段、测点资料适用性和仓库发布记录；标记 JSON 是否漂移 | 默认无；`--write` 仅重建同版本 JSON |
| 推进生命周期 | `& .\scripts\model-lab.ps1 advance` | 先执行当前阶段门禁并展示计划 | 仅显式 `--apply` 后推进本地状态；当前最多到 releasable |
| 核对每步交付物 | `& .\scripts\model-lab.ps1 step-check <工作区>` | 按工作流步骤表逐步骤报「已完成 / 部分完成 / 未产出」+ 缺什么 + 怎么补，只判当前前沿 | 无；`--write-context` 只刷新仓库 `.dsh-hooks/context.md`；`--strict` 把历史缺口也判失败（默认只判当前前沿） |
| 发布与归档 | `& .\scripts\model-lab.ps1 publish` / `& .\scripts\model-lab.ps1 archive-release` | 预览授权、归档记录前置与远端写入计划 | 仅显式 `--apply`（publish 还需用户逐次授权）后上传并留回执；`released` 只由 `archive-release --apply` 写入 |

`model-lab` 是公共 seam；模板选择、路径生成、清单校验和阶段门禁均属于其内部实现。`maintain` 用于已发布模型的行为不变补丁或独立契约升级，不是同 ID 的普通 `new`。进入发布准备后，兼容诊断命令 `dry-run` 负责生成确定性试运行计划；它保持只读，不是第二套建模流程。
`context` 是只读导航/生成入口，不是第二套生命周期；`workflow-state.json` 随正常
写入命令自动刷新。Codex hook 只提示，不改仓库，后备入口见
[状态快照与 Hook](./07-模型状态快照与Hook.md)。
未发布草稿不得伪装为 `maintain` 的 released 父版；如已验证的数值草稿需改成测点数组，使用 `draft-fork <草稿> --version <下一次版本>`。该入口只复制仍不变的公式/源码及行为对照，测点字段、时间策略、在线验收与发布计划在新版重新确认；父草稿不得覆盖。
技术构建命令 `bundle-build` 同样不形成第二套生命周期：它默认预览，显式
`--apply` 仅从当前模型的 `src/model.py` 与指定样本生成本地 MLflow service，
不推进状态、不扫描仓库其他模型、不写远端。

## 任务分流

| 用户意图 | 路由 | 最小加载 | 结果 |
|---|---|---|---|
| 首次使用、更新环境、配置模型根 | `setup` | 本页、`04-人工操作快速开始` | 检查依赖并按需写入本机配置（`--models-root <仓库外私有目录>`） |
| 恢复或记录任务计划与交互档位 | `task-plan` | 本页、`06-模型任务问答与交互档位`、ADR 0018 | 读取或落盘任务卡，恢复交互模式与下一步 |
| 新模型、新厂模型、首次登记 | `new` | 本页、`11-新模型开发SOP`、ADR 0008 | 在 `_drafts` 中规划或创建模型工作区 |
| 查询进度、缺什么、下一步做什么 | `status` | 本页、目标 `model.yaml` | 只读状态报告，不改变资产状态 |
| 完成当前阶段、申请状态推进 | `status` 后 `advance` | 当前阶段对应 SOP 小节和证据文件 | 门禁通过才允许本地推进 |
| 生成发布前试运行计划 | 兼容诊断 `dry-run` | 已 validated / releasable 的 `model.yaml` | 输出确定性计划 ID、目标适配器、制品摘要和只读步骤；无远端写入 |
| 修复在役模型 | `status` 后用 `maintain` 建新补丁工作区 | 本页、目标清单、现有参数确认记录及基线 | 原在役目录不变；独立工作区从 draft 走到 releasable |
| 未发布数值草稿更改平台输入模式 | `status` 后用 `draft-fork` 建下一次版本 | 本页、父草稿清单/决定/行为证据、测点契约规则 | 同 ID 新草稿从 draft 重新走门禁；父草稿不变 |
| 上传、写 MLflow | `publish` 预览后显式 `--apply` | ADR 0004、ADR 0012、ADR 0016、ADR 0017 | 使用者只提供平台实验名和作者标识；首个适配器仅支持已验收 CPU-IoT 测点模型固定实包，其他目标明确阻断；不运行旧脚本重建实包 |
| 已有成功 Run，补核验或机器回执 | `context` 后用 `verify-publication` | 目标 `model.yaml`、在线验收与已知实验/Run ID | 远端只读复核同一实包；通过后仅写本地逐 Run 回执和状态索引，不创建新 Run |
| 公司业务平台任务或生产调度 | 独立任务，非 `publish` 的后置门禁 | ADR 0017 | 仅在用户要求该链路时验证或启用；一次性演示可保持无调度 |
| 核对每步交付物、看本阶段还缺什么 | `step-check` | 本页、目标工作区、当前阶段的 SOP 小节 | 逐步骤状态 + 缺什么 + 怎么补；越界产物只单独提示，不并入退出码 |
| 每步核对并登记台账 | `step-check` 后 `ledger set`，再用 `ledger check` 复核 | 本页、目标工作区、当前阶段 SOP 小节 | 台账逐步骤记 status/owner/evidence（append-only，status 只是声称）；`ledger check` 0＝与重算一致、1＝漂移，只影响 ledger 子命令，不改 `step-check` 退出码与门禁结论 |
| 查看全库健康与中央目录 | 兼容诊断 `release-gate` / `catalog` | 本页、各清单生成结果 | 只读校验正式资产、草稿清单和当前草稿树 |
| 版本更新前核对或正式发布前终审 | 查阅核对规程并执行门禁合闸 | 本页、`08-框架全景流程与发布核对清单` | 执行四道硬门禁、目标环境实包验证与全量回归核对 |

## 智能体技能分流

自然语言入口统一先由 `model-lab-router` 判断场景；使用者不需要手工串联全部技能。

### 技能与工程分工

仓库智能体由通用工程支撑技能与模型实验室生命周期技能共同组成，分工明确：
- **任务与规格管理**：由私有 GitHub Issues 负责，详见 [`docs/agents/issue-tracker.md`](../agents/issue-tracker.md)；
- **需求标签与流转**：通过五类分类标签流转，详见 [`docs/agents/triage-labels.md`](../agents/triage-labels.md)；
- **领域语言与架构决策**：根目录 `CONTEXT.md` 维护通用领域词汇，`docs/adr/` 维护架构决策记录，详见 [`docs/agents/domain.md`](../agents/domain.md)；
- **模型生命周期的 7 个技能**：5 个场景技能（`model-requirements-grill`、`model-data-audit`、`model-build-validate`、`model-runtime-release`、`model-maintenance`）+ `model-lab-setup`（环境类，不占生命周期场景）+ `model-lab-router`（只做分流指针，路由与加载事实以本页为准）。技能事实源与维护说明见 [`docs/agents/model-lab-skills.md`](../agents/model-lab-skills.md)。

| 场景 | 场景技能 | 交互重点 |
|---|---|---|
| 新模型、需求或算法口径未冻结 | `model-requirements-grill` | 用途、契约、验收、公式、参数、测点和边界 |
| 数据可用性、测点映射或异常处理 | `model-data-audit` | 自动计算数据事实，只让负责人决定处理口径 |
| 编码、Notebook、测试、图表和基线 | `model-build-validate` | 自动构建验证，确认结果是否达到验收口径 |
| Python、MLflow、GPU/Chronos、发布准备 | `model-runtime-release` | 环境事实、制品门禁、部署回滚和限定事务授权 |
| 在役模型的修复或演进 | `model-maintenance` | 保留历史，区分部署修复与行为新版本 |
| 新机器、新克隆、环境与部署能力自检 | `model-lab-setup` | 环境类，不占生命周期场景；验证 Python 3.11、WSL、技能同步与部署能力 |
| 不知道该走哪条流程 | `model-lab-router` | 只是指向本页的指针；路由事实以本页为准 |

所有技能都使用同一个 `model.yaml`、`decisions.yaml` 和生命周期工作流。智能体在
一个已交办模型任务内连续执行本地步骤，不在每次 `new --apply`、
`bundle-build --apply` 或 `advance --apply` 前重新询问授权；门禁失败、业务口径
改变或超出工作区范围时才停下。Git 远端与真实发布使用明确的限定事务指令。
Ask Matt 可以继续作为个人的通用技能选型入口，但不是本项目运行的依赖。

新可写任务第一次回复须展示一次 `full-auto`、推荐的 `assisted`、
`manual-review` 三档选择；已选择或续办同一任务时不重问，纯只读任务不弹。
选择之后按[任务问答与交互档位](./06-模型任务问答与交互档位.md)的场景表提问：
行为不变迁移不重做新模型问卷，契约升级只问差异，数据和测试事实先自动查，
发布只补缺失的模型编号和作者标识。独立业务决定同轮合并询问，不为每个本地
`--apply` 命令单独要许可。三档都不能代答开放的必填决定或绕过发布适配器
的实包、环境与在线验收门禁，且不按 CPU/GPU/Chronos 拆技能。详见
[ADR 0014](../adr/0014-部署交互档位与硬门禁分离.md)。

## 固定顺序

```text
new（默认只预览）
  -> new --apply（创建模型工作区）
  -> status（查看当前阶段和缺口）
  -> 完成阶段证据
  -> advance（默认只预览）
  -> advance --apply（门禁通过后推进）
  -> 重复 status / advance，先到 releasable
  -> dry-run / publish（只读预览）
  -> publish --apply（仅已支持的适配器；远端回载与预测后保存发布证据）
```

不得跳过状态、手工改 `model.lifecycle_state`、手工复制模型模板、手工把目录从 `_drafts` 移到在役层，也不得把一次检查失败写成新的资产状态。

在役模型先判断是补丁还是在线契约升级，采用 `status <旧目录> → maintain <旧目录> --version <新版本> [--change-kind contract-upgrade]`，
预览后显式 `--apply`，再对新目录执行 `status/advance`。旧目录继续保持
`released`；若旧版没有可信固定输入行为基线，新目录停在门禁前补证据，
不得把“脚手架创建成功”称为部署成功。详见 [ADR 0015](../adr/0015-在役模型维护版必须安全分叉.md)。

三个入口只接受本地文件系统路径，不访问 UNC、设备路径或映射网络盘。
`status` / `advance` 不导入或执行草稿源码与 Notebook；实现、测试和 Notebook
先由开发者在受控环境运行，再把命令、结果和摘要写入阶段证据。

## 最小加载矩阵

1. 所有模型任务先读 [`00-模型开发总览.md`](./00-模型开发总览.md) 和本页；
   可写任务再读 [`06-模型任务问答与交互档位.md`](./06-模型任务问答与交互档位.md)。
2. `new` 只补读 ADR 0008 与 SOP 的需求、设计部分；不预读部署运行时和全部历史模型。
3. `status` 只读取目标模型资产清单、阶段证据和当前工作区安全边界；全库检查才读取全部清单。
4. `status` 同时读取目标工作区的 `decisions.yaml`；只展示当前转换的开放问题，不把未来阶段问题一次性塞给使用者。
5. `advance` 只加载当前阶段门禁所引用的决定和证据；进入验证或发布准备时再加载运行环境与 MLflow 制品 SOP，并按需显式调用只读 `dry-run`。
6. 涉及在役模型修复时读取该模型现有发布快照和行为基线，用 `maintain` 校验父版本摘要并建立新工作区；不把其他在役模型作为模板。
7. 涉及真实发布时检查是否为 ADR 0016 已实现的目标与验收档；网络不可达或目标未实现时报告具体阻塞，不能仅凭实验号或作者标识宣称已发布。
8. 对使用者只询问无法从当前上下文取得的平台实验名和发布作者标识；`--target` 可从已验证的 `model.yaml` 自动确定，不把平台连接地址、Python ABI 或制品摘要变成重复问答。

## 调用示例

以下命令使用当前公共 Interface：

```powershell
# 预览脚手架计划；显式 --apply 后才创建模型工作区
& .\scripts\model-lab.ps1 new hydraulic-delay-new --name "新水力延时模型" --target cpu-iot --owner heshengjie
& .\scripts\model-lab.ps1 new hydraulic-delay-new --name "新水力延时模型" --target cpu-iot --owner heshengjie --apply

# 状态只读；推进默认也先给计划
& .\scripts\model-lab.ps1 status models/_drafts/hydraulic-delay-new
& .\scripts\model-lab.ps1 advance models/_drafts/hydraulic-delay-new
& .\scripts\model-lab.ps1 advance models/_drafts/hydraulic-delay-new --apply

# 仅当清单已到 validated / releasable 时生成只读试运行计划
.\.venv-311\Scripts\python.exe -m model_lab dry-run models/_drafts/hydraulic-delay-new/model.yaml --format json
```

## 完成判定

- `new` 完成：计划与实际文件一致、目标位于 `_drafts`、模板版本可追溯、没有制品或凭据进入 Git。
- `status` 完成：明确当前资产状态、通过与失败的门禁、下一动作；不产生写入。
- `advance` 完成：只推进一个合法状态转换，并返回新状态与下一阶段门禁；门禁失败时保持原状态。确定性发布试运行计划由显式只读 `dry-run` 返回。
- MLflow 发布完成：`publish --apply` 回执成功，真实 Run 完成、同一实包回下载摘要一致且平台路径预测通过；不要求业务平台任务调用、启用调度或 Git 推送。
- 已有 Run 的补录完成：`verify-publication` 核对实验归属、`FINISHED` 状态、包摘要和平台路径预测后保存机器回执；核验失败不新建 Run，也不把历史文字记录升级为已验证状态。
