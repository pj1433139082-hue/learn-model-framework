# 测点模型时间与字段角色（#16）

每个测点模型在 `serving` 中显式声明 `time`、`rolling_window` 和 `interval`；缺一项不能构建。`time.strategy` 支持 `explicit-start`、`target-date-day` 和 `latest-complete`，不支持未声明规则的“运行当天”。`explicit-start` 由 `start_field` 接收完整时间字符串：无偏移量时按 `time.timezone` 解释，有偏移量时先转换到该时区；`target-date-day` 由 `start_field` 接收 `YYYY-MM-DD`，窗口必须明确写 `1d`，覆盖该时区的本地全天。两种策略都将本地窗口起点格式化为公司 `fetch_iot_data` 的 `start_time`。

`latest-complete` 仅用于 `feature_adapter: source-history-v1`。它要求显式声明能整除一天及回看窗口的 `time.period`（例如 `30min`）；默认由服务端当前时间在 `time.timezone` 中向下对齐到最近已结束的周期边界，从该边界向前取 `rolling_window`。`start_field` 是可选的**回放截止参考时间**，未提供时不进入 MLflow 必填签名，不能把固定日期当成日常输入。显式回放时间仍支持带/不带偏移量的完整时间字符串。运行时严格截掉公司接口返回的窗口外记录；调用模型的 `prepare_features(raw, request)` 时，`request.attrs` 提供带时区的 UTC 时间戳 `model_lab_window_start_utc` 与 `model_lab_window_end_utc`。模型必须据此选择最近周期并核对测点采样质量，不能从返回的最后一条数据反推周期，也不能仅凭 `interval` 请求值认定采样完整。

如果真实接口存在有证据的数据发布延迟，可在 `latest-complete` 的 `time` 中声明可选 `availability_lag`，值必须是正整数个 `period`，例如 `period: 15min` 配 `availability_lag: 15min`。运行时先将当前时间或显式回放参考时间减去该滞后，再对齐周期边界；缺省仍为零滞后。它只改变**请求的截止周期**，不允许用更早的已有数据偷偷替代该周期，周期首尾、采样间隔及无效值仍须由模型检查。配置滞后会降低结果的新鲜度，必须在模型设计里说明并确认。

```yaml
serving:
  mode: point-code
  factory_field: factory_code
  point_fields: [Flow1(m3h), Flow2(m3h)]
  start_field: as_of_time
  feature_adapter: source-history-v1
  time:
    strategy: latest-complete
    period: 30min
    timezone: Asia/Shanghai
    iot_timestamp_timezone: UTC
  rolling_window: 120min
  interval: 15s
  binding: input-bindings.yaml
```

上例是时间策略形状，不是已核准的测点绑定。`latest-complete` 只确定取数边界；具体模型须定义最近周期缺样、无效值和失败策略。公司接口的真实生产取数语义仍按模型在目标环境验收。

```yaml
serving:
  mode: point-code
  factory_field: factory_code
  point_field: Flow1_inst(m3h)
  start_field: target_date
  time:
    strategy: target-date-day
    timezone: Asia/Shanghai
    iot_timestamp_timezone: UTC
  rolling_window: 1d
  interval: 15s
  control_fields: [air_setpoint]
  evaluation_fields: [Q_ff_B_target]
  binding: input-bindings.yaml
```

`point_field` 或 `point_fields` 对应算法数值特征，但服务签名为测点编码数组。`control_fields` 是真正参与算法计算的数值设定值，必须列在 `contract.inputs` 的测点特征之后。`evaluation_fields` 是可选的数值核对值，不列入 `contract.inputs`，运行时不传给算法；即使请求没有它也能预测。字段名以 `_target` 结尾时，`model-lab validate` 会显示非阻断的角色复核提示；后缀不会自动决定角色，应由模型负责人确认后显式填写。数值模式模型不受此结构影响。

例外是 `source-history-v1`：平台的 `point_fields` 仍是测点编码数组，而 `contract.inputs` 可以声明由整段历史计算得到的另一组数值特征，例如“平滑液位差”和“周期流量均值”。此时 `prepare_features` 必须返回**恰好一行**、列名和顺序均与 `contract.inputs` 一致的数值特征；绑定文件的测点单位仍须与实测信号一致，不能把派生特征名伪装成原始测点名。非历史的 `latest` 适配器仍要求算法输入与测点字段及控制字段逐一对应。

由于公司接口 `rolling_window: 1d` 的真实时长语义仍待 #19 核验，`target-date-day` 暂时拒绝夏令时导致不足或超过 24 小时的本地日期，不宣称这些日期已覆盖整天。IoT 返回必须带 `data_time`。无时区的返回值按 `iot_timestamp_timezone` 解释；带偏移量的返回值直接转换到模型时区。`feature_adapter: latest` 只使用请求窗口内时间最新的一行，各测点取自同一行；`source-history-v1` 则把截窗、排序和去重后的完整历史交给模型的 `prepare_features`，由模型逐周期核对质量。窗口外、无效时间、缺少必要数值、非有限特征、接口失败或空结果均不得形成预测，不用 mock、零或旧数据回退。当前服务只接收一条平台记录。跨夏令时切换的无时区平台时间若有歧义或不存在，会要求调用方改为带偏移量的时间。
