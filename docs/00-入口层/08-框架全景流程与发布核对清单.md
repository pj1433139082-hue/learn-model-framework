# 08-框架全景流程与发布核对清单

> 本文档面向所有使用与维护本框架的工程师、算法研究员与 AI 智能体。
> 包含两项核心使命：
> 1. **全景认知**：向使用者完整展示框架端到端生命周期工作流与核心能力体系；
> 2. **标准核对规程**：在**更新模型/框架版本之前**以及**正式向平台发布上线之前**，提供可逐项打勾执行的标准核对清单（Checklist）。

## 一、框架核心功能矩阵

本框架面向高可靠工业水务场景设计，为算法模型从离线研发到工业级上线提供全生命周期工程约束与质量防护：

| 功能模块 | 核心能力 | 对应工具 / 载体 | 核心价值 |
|---|---|---|---|
| **脚手架与生命周期** | 标准化创建、演进与版本分叉 | `& .\scripts\model-lab.ps1 new` / `maintain` / `draft-fork` / `advance` | 消除手工复制代码模板引发的错误，强制状态单向递进 |
| **契约驱动规格** | 输入输出签名、时间粒度与点位强绑定 | `model.yaml` / `input-bindings.yaml` / `model-spec.md` | 接口契约化，消除算法特征与底层数据流的歧义 |
| **四道质量硬门禁** | 环境、目录、快照与制品全维度自动化核验 | `doctor` / `catalog` / `context` / `release-gate` | 离线确定性防御，杜绝坏味道代码与不合规模型进入仓库 |
| **双运行时解耦** | 本地 Windows 开发控制面 + Linux 生产执行实包 | `bundle-build` / `bundle-preflight` / WSL (Ubuntu) | 在本地即可完全复刻云端 Linux 生产环境并跑通预测 |
| **智能体协同矩阵** | 7 大生命周期专用技能与双轴代码审查 | `.skillshare/` 技能库 + Standards / Spec 双轴审查 | 规范人机协作边界，提供确定性的引导与自动化守护 |
| **安全分发与脱敏隔离** | 通用框架代码与私有业务模型物理隔离 | `& .\scripts\model-lab.ps1 distribute` + 隐私门禁扫描 | 保证开源框架通用性，同时彻底杜绝业务敏感信息泄露 |

每个水务模型都必须严格遵循 **六阶段状态机**，不可跨阶段跃迁：

```text
 ┌───────────────┐
 │   Stage 0     │ 环境准备与引导 (Setup & Doctor)
 │   Bootstrap   │ -> 运行 model-lab-setup 自检，确认 Python 3.11 与构建环境
 └───────┬───────┘
         ▼
 ┌───────────────┐
 │   Stage 1     │ 契约与规格设计 (Draft -> Specified)
 │   Contract    │ -> model-lab new 生成草稿，定义 model.yaml 与 input-bindings.yaml
 └───────┬───────┘
         ▼
 ┌───────────────┐
 │   Stage 2     │ 算法研发与验证 (Specified -> Built -> Validated)
 │  Development  │ -> 实现 src/model.py，编写单测与 Notebook，产出 plots 与报告
 └───────┬───────┘
         ▼
 ┌───────────────┐
 │   Stage 3     │ 目标环境实包构建 (Validated -> Releasable)
 │   Packaging   │ -> 目标 Linux Python 3.11 构建 release-bundle/service 并完成预测核验
 └───────┬───────┘
         ▼
 ┌───────────────┐
 │   Stage 4     │ 全量门禁与版本核对 (Pre-Release Audit)
 │   Auditing    │ -> 跑通四道门禁 + 全量回归 + 补充 CHANGELOG.md + 双轴代码审查
 └───────┬───────┘
         ▼
 ┌───────────────┐
 │   Stage 5     │ 显式授权发布与留档 (Releasable -> Released)
 │  Publication  │ -> 逐次授权后 publish --apply 上传留回执；archive-release 归档后状态才进 released
 └───────────────┘
```

### 各阶段输入、产出与推进命令对照

| 阶段 | 初始状态 | 目标状态 | 核心任务 | 关键产出文件 | 推进命令 / 门禁 |
|---|---|---|---|---|---|
| **0. 自检** | - | READY | 检查 Python 3.11 控制面、技能与 Linux 构建环境；登记仓库内私有模型根（`models`）与公司能力包路径 | `.model-lab.local.json`（由 `setup --apply` 写入，`doctor` 只读不写） | `python -m model_lab doctor .` + `python -m model_lab setup --models-root models --company-iot-zip <公司ZIP> --apply` |
| **1. 设计** | `draft` | `specified` | 明确业务诉求、点位映射与算法输入输出契约 | `model.yaml`, `input-bindings.yaml`, `decisions.yaml` | `& .\scripts\model-lab.ps1 advance <path> --apply` |
| **2. 研发** | `specified` | `built` / `validated` | 编写模型算法源码、高精基准测试与可视化审查 | `src/model.py`, `tests/test_model.py`, `plots/*.png` | `advance --apply`（需单测与证据全过） |
| **3. 打包** | `validated` | `releasable` | 在 Linux 3.11 构建自包含 MLflow 服务实包并预检 | `release-bundle/service/`（`bundle-preflight` 只输出报告、不落盘）；点码模型还需 `validation/online-acceptance.json` | `bundle-build` + `bundle-preflight` + `advance --apply`（点码模型先用 `model-lab record-online-acceptance` 生成在线验收回执） |
| **4. 审计** | `releasable` | 门禁就绪 | 跨平台回归测试、更新变更记录、通过四道门禁 | `CHANGELOG.md`, `git diff` | 四道硬门禁全通过 + 双轴审查 PASS |
| **5. 发布** | `releasable` | `released` | 获得明确授权后上传制品、留存发布回执并写归档记录 | `publish-receipt.json`, MLflow 平台 Run, `docs/90-归档/<NN>-<名>-<版本>-归档记录.md` | `publish --apply`（上传，必须用户显式授权）→ `archive-release <model.yaml> --documentation <归档记录> --apply`（唯一写入 `released` 的命令） |

## 三、人机交互前置确认与固定问卷导航规程（Handshake & Questionnaire）

为了杜绝开发者或智能体在未核实现场边界前盲目假设编码，框架将人机沟通严格拆解为**“人机交互档位与决策分级”**、**“固定问卷（标准化单选/必填项）”**与**“非固定开放探讨（工艺/现场策略）”**：

### 1. 人机交互档位与决策分级矩阵（正交对照表）

智能体协作的交互频率由**交互档位**决定，而每个问题的严肃程度由**决策级别**决定。两者正交组合，构成清晰的暂停与推进规则（ADR 0010、0014、0026）：

#### (1) 四类决策级别（问题性质）
- **`AUTO`（事实级）**：环境检查、代码静态分析、单测执行、指标比对。系统自动收集证据并落盘，**绝不向用户提问**，直接推进；
- **`ASK`（信息级）**：缺失事实或背景信息（如任务背景、说明文档链接、责任人姓名）。智能体提供推荐值，用户可单轮确认；
- **`CONFIRM`（决策级）**：会改变模型计算行为、输入输出契约、异常处理、数据来源或验收标准的业务决定。**在 `decisions.yaml` 登记前始终硬性阻塞推进**；
- **`AUTHORIZE`（事务级）**：向 GitHub 远端推送（`git push`）、合并 PR、修改生产调度、正式向云端发布（`publish`）。**必须单次逐次显式授权，严禁自动确认**。

#### (2) 三种交互档位与暂停行为对照

| 决策级别 | ① 全自动 (`full-auto`) | ② 半自动 (`assisted`, 默认推荐) | ③ 逐步确认 (`manual-review` / 仔细提问) |
| :--- | :--- | :--- | :--- |
| **`AUTO` 事实级** | 连续执行，静默记录证据 | 连续执行，阶段完成给简报 | 执行前展示命令与计划，确认后执行 |
| **`ASK` 信息级** | 使用已确认事实；首次遇缺失集中询问 | 集中同一轮提问并附推荐答案 | 逐项展示缺失字段与推理证据，确认后再填 |
| **`CONFIRM` 决策级** | 遇到必填决定时停下，集中询问 | 同阶段独立问题合并一轮，附带推荐选项 | 逐阶段逐项展示计划、影响与备选项，逐个确认 |
| **`AUTHORIZE` 事务级** | **绝不自动**，必须明确指令 | **绝不自动**，单独一次限定事务授权 | **绝不自动**，逐个事务单独提示并核对差异 |

### 2. Stage 0 开局基建自检与任务前置握手（固定必答项）

在新建模型或接手维护任务的第一分钟，智能体/开发者必须对照以下 4 项进行基建与任务确认：

| 序号 | 核心问题项 | 标准化选项 / 沟通内容 | 落地与约束影响 |
| :--- | :--- | :--- | :--- |
| **0.1** | **解释器与环境基线** | • **控制面 Python 3.11**：必须是 `>=3.11,<3.12`，运行 `& .\scripts\model-lab.ps1 doctor .`<br>• **双速运行基准**：Windows 本地为开发主环境，WSL Linux 为按需发布预检环境<br>• **公司部署能力包**：核验 `infra_model_deploy.zip` 哈希（`06f08382...`） | 必须满足，否则禁止开工 |
| **0.2** | **任务与 Issue 载体** | • A. **GitHub 远端 Issue**（协作标准，需提供 `#ID`）<br>• B. **本地 Markdown 规格**（单机离线模式，编写在 `docs/`） | 决定 Git 提交与追溯绑定 |
| **0.3** | **生命周期演进模式** | • A. **新建全新模型**（`& .\scripts\model-lab.ps1 new <name>`，起始 `0.1.0`）<br>• B. **在役模型缺陷补丁**（修复 Bug，发 `x.y.z+1` 补丁）<br>• C. **在役模型契约升级**（新增点位/重构，发 `x.y+1.0` 次版本） | 决定目录脚手架与血统分支 |
| **0.4** | **专属技能与安全红线** | • **专属技能按需授权**：如是否需要 `diagram-design` / `water-quality-experiment`？<br>• **安全红线握手**：禁用 `git rm`、私有数据严禁入 Git、远端推送逐次显式授权 | 明确当前会话安全基线 |

### 3. Stage 1-2 契约数据与算法路线（固定必答项）

在推进至 `specified` 与 `built` 之前，必须收敛以下 5 项接口、数据源与算法参数（ADR 0026）：

| 序号 | 核心问题项 | 标准化选项 / 沟通内容 | 落地与约束影响 |
| :--- | :--- | :--- | :--- |
| **1.1** | **数据获取源与防偷懒门禁**<br>*(requirements-data-source)* | • A. **现场动态拉取（`live-iot` - 推荐）**：对接真实数采，必须调用 IoT 加载器生成回执凭证（`iot-pull-receipt.json`）。**工作区严禁私留未纳管表格，违者门禁判 FAIL**<br>• B. **离线静态基准文件（`static-baseline`）**：使用经确认的本地基准文件，必须在决策中登记降级原因并在模型中记录 `offline-only`，阻断无凭证上线 | 彻底杜绝偷懒用本地数据假冒真实数采 |
| **1.2** | **现场数据输入形态** | • A. **离线静态表格（Excel / CSV）**：包含时间戳与多列原始数据<br>• B. **真实数采测点编码数组（Point-Codes）**：对接 `company-iot-311`，在 `input-bindings.yaml` 映射 | 决定输入适配层走表格还是点位模式 |
| **1.3** | **计算频率与调度周期** | • A. **10 分钟**（标准中控周期）<br>• B. **5 分钟** / **1 分钟**（敏捷高频调节）<br>• C. **1 小时**（报表级预测） | 决定时序滑动窗口与滞后步长 |
| **1.4** | **多探头冗余聚合规则** | • A. **双/多探头取均值（mean）**（如缺氧末端双探头）<br>• B. **取极值（max/min）**（保守防穿透）<br>• C. **单探头独占（single）** / **主备回退（fallback）** | 写入 `input-bindings.yaml` 聚合规则 |
| **1.5** | **算法路线与依赖纯洁度** | • A. **纯物理/化学机理公式**（全代码实现，无外部权重文件）<br>• B. **统计/机器学习模型**（含 `.pkl`/`.joblib` 权重）<br>• C. **深度时序/AI 基础模型**（PyTorch / Chronos）<br>• **依赖纯洁度**：严禁引入未在部署包内声明的第三方私有库 | 写入 `model.yaml` 与依赖清单 |

1.1 的 `live-iot` 现场取数如果要在**不在公司内网**的机器上执行，先按
[24-无VPN取数与公网路径验证手册](../10-流程层/24-无VPN取数与公网路径验证手册.md) 判定该机走公网还是内网路径：
取数本身不需要 VPN，发布与在线验收仍必须内网。

### 4. Stage 3-5 生产实包与发布预检（双速架构按需选项）
在进入实包构建（`bundle-build`）与正式发布（`publish`）前，根据宿主环境按需确认：

| 序号 | 核心问题项 | 标准化选项 / 沟通内容 | 落地与约束影响 |
| :--- | :--- | :--- | :--- |
| **3.1** | **目标运行环境保真质检**<br>*(target_runtime_preflight)* | • A. **目标 Linux 生产保真质检（WSL Linux Preflight）**：调用 WSL 运行 `& .\scripts\model-lab.ps1 test-profile linux-offline` 验证 Linux `.so` 兼容性与容器路径敏感性<br>• B. **跳过本地 Linux 预检（开发机未配置 WSL 或日常快速演练）**：在验证报告中诚实标注 `validation.platform_parity_skipped: true` 与降级审计理由，交由生产流水线把关 | 兼顾极速研发与生产保真审计 |

### 5. Stage 1-5 现场工艺与极端工况（非固定开放探讨项）

针对水务现场真实的物理现实，智能体/开发者需与业务人员深度探讨，并将结论固化在 `model-spec.md` 与 `decisions.yaml` 中：

1. **探头故障与断流保底策略**：现场传感器结垢、零值漂移或网络丢数时，是采用最后有效值前向填充、当日历史均值回退，还是按工艺安全上限硬截断？
2. **冲击工况与参数分支切换**：暴雨雨季大水量、暴雪低温冬季工况下，机理公式常数或模型阈值如何动态切换？
3. **离线验收样本规格与精度要求**：是采用单条冷启动冒烟，还是连续 24 小时（48~144 条）时序回放？绝对数值误差还是统计回归指标（MAPE）？
4. **线上安全告警与故障回滚预案**：上线后重点监控哪些告警指标（如 DO/氨氮超标预警）？异常时切回哪一版稳定模型或回退传统 PLC 人工设定值？

## 四、更新版本之前核对规程（Pre-Update Checklist）

无论对模型做版本升级（如 `0.1.0` -> `0.2.0` / `1.0.0`），还是迭代通用框架底层代码，在**合并代码或提交版本变更前**，必须逐项核对：

### 1. 契约与接口核对
- [ ] **语义化版本号合规**：
  - 补丁修复（Bugfix / 平台行为不变）：增加 Patch 版本号（如 `1.0.0` -> `1.0.1`）；
  - 测点增加 / 功能扩展（向后兼容）：增加 Minor 版本号（如 `1.0.0` -> `1.1.0`）；
  - 签名破坏 / 算法输入输出重构：增加 Major 版本号（如 `1.0.0` -> `2.0.0`）。
- [ ] **元数据清单与输入绑定对齐**：
  - `model.yaml` 中的输入输出字段名、类型与 `input-bindings.yaml` 100% 一致；
  - 点位聚合规则（如双探头 `mean`、单探头 `latest`、流量 `diff`）明确标注且经业务确认。
- [ ] **决策记录无悬挂**：
  - `decisions.yaml` 中的所有必填决策项（`CONFIRM`）均已标记为 `confirmed` 并附带确认人，无遗留未决项。
- [ ] **文件摘要钉住（SHA256 Pinning）**：
  - `model.yaml` 中的 `source.entrypoint`、`source.notebook`、`source.specification` 的 `digest_sha256` 已重新计算并更新为最新的 `utf8-lf` 哈希。

### 2. 代码与环境纯洁性核对
- [ ] **Python 3.11 绝对基线**：
  - 全仓所有执行链路与虚拟环境均为 Python 3.11（推荐 3.11.15），无任何 Python 3.12 专属语法或隐式依赖。
- [ ] **零污损工作树**：
  - 工作区不包含任何未纳管的临时测试表格（如 `benchmark.csv` 等），禁止私自将原始数据带入 Git；
  - 模型草稿目录下绝无 `__pycache__` 或 `.pytest_cache` 目录（可运行清理命令 `Get-ChildItem -Path models -Filter __pycache__ -Recurse | Remove-Item -Recurse -Force`）；
  - 本地历史资产模型目录下的 `*.pkl` 真实权重文件保持不动，不破坏原状。
- [ ] **无凭据与隐私保护**：
  - 源码、注释、Notebook 与文档中严禁包含数据库密码、平台 Token、真实内网 IP 或未经许可的敏感信息。

### 3. 自动化测试核对
- [ ] **领域模型测试全绿**：
  - 模型的单元测试继承标准 `unittest.TestCase`，所有测试用例通过（OK）；
  - 现场实测基准数据与算法输出浮点误差小于 $10^{-8}$。
- [ ] **可视化图表规范**：
  - 生成的图表（`plots/*.png`）全部使用全英文坐标轴与图例，无中文方框乱码（□□□□），画面无视觉遮挡。

  - 回执已存在时拒绝覆盖；确需重记用 `--replace`，命令先打印将被丢弃的旧摘要（sha256、profile、记录时间、字节数）再写。写完立即用 `verify_online_acceptance` 重新加载复核，校验不过则删除新文件（`--replace` 时恢复旧字节）并报 `acceptance_receipt_rejected`。
  - `advance`、`publish` 等门禁照旧读同一个 `validation/online-acceptance.json`，命令没有放宽任何校验；回执仍是本地证据，不是平台背书。
