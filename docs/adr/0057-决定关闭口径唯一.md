# 0057 决定关闭口径唯一：answered 不是关闭态

> 本 ADR 保留私有源仓原文；`step-check`、`ledger`、`.dsh-hooks` 在本公开框架分发仓未实现，请以 `status`、`context`、`.codex/hooks.json` 为准。

- 状态：已接受
- 日期：2026-10-21

## 背景

同一份 `decisions.yaml` 在两处得到相反结论：

- `model_lab/decisions.py` 的登记册只允许 `open | confirmed | superseded`，
  `answered` 会被判 `decision_status_invalid`；
- `model_lab/step_check.py` 的 `_decision_closed` 却把 `{answered, confirmed}` 都算关闭，
  于是第 1 步可能判 `done`，而 `advance` 的门禁又因登记册非法而拒绝。

`answered` 只出现在测试夹具里（`tests/test_step_check.py` 三处），真实清单全部用 `confirmed`。
这不是两种合法状态，而是一处漏改留下的第二套词表。

## 决策

1. **关闭态只有两个**：`confirmed`（用户拍板）与 `superseded`（被后续决定取代）。
   `CLOSED_STATUSES` 定义在 `model_lab/decisions.py`，别处不许再写状态集合。
2. **两个公开谓词**：`is_closed(status)` 与 `is_blocking(status=, required=, level=)`；
   阻塞＝未关闭且（`required` 为真或 `level == "CONFIRM"`）。
3. **所有调用点改用谓词**：`step_check._decision_closed`、`step_check._decision_items`、
   `lifecycle` 的 `interaction-decisions-confirmed` 门禁都调同一实现。
4. **`answered` 不是关闭态**：夹具改用 `confirmed`；新增用例断言 `answered` 仍算阻塞。
5. **登记册状态表不扩**：不把 `answered` 加进 `_STATUSES`，避免出现「两种都能关闭」的第三套口径。

## 后果

- 历史工作区若真写了 `answered`，`step-check` 会把该决定判为未关闭、第 1 步回到部分完成——
  这与登记册校验、`advance` 门禁原本的结论一致，只是提前暴露。
- `tests/test_delivery_verdict.py::DecisionClosureTests` 固化两种谓词的真值表；
  `tests/test_step_check.py` 用真实工作区夹具断言 `answered` 不关闭。
- `docs/00-入口层/07` 与 SOP 不需要新增状态说明：词表仍是三态。

## 被否决方案

- **把 `answered` 加进登记册**：等于承认两套关闭词，后续每处都要判两次。
- **保留 `step_check` 的双状态、只改文档**：代码仍会在第 1 步给出与门禁相反的结论。
- **在 `step_check` 里内联 `status != "open"`**：又把「哪些状态算关闭」复制了一份。
