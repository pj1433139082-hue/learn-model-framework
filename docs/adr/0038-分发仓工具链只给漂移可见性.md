# 分发仓工具链只给漂移可见性

状态：已接受（2026-10-16）

## 背景

私有仓的安全分发（`model-lab distribute`）白名单只有 `docs/` 与 `models/`，`model_lab/**` 从来不在分发面内。但公开分发仓 `learn-model-framework` 带着**整套手工维护的工具链副本**（`model_lab/`、`tests/`、`scripts/`、`pyproject.toml`），既没有同步通道，也没有漂移门禁。2026-10-15 实测（issue #48）：

- 私有仓 `model_lab/*.py` **40 个** vs 分发仓 **31 个**；同名 33 个里**逐字节一致只有 3 个**；
- 只在私有仓存在的 9 个是 `archival.py`、`ast_guard.py`、`distribution.py`、`document_loader.py`、`findings.py`、`gpu_publish.py`、`inventory.py`、`security_audit.py`、`verdict.py`——正是核心深化的产物；
- 偏离**不是单向的**：`online_acceptance.py` 私有 29,117 字节 vs 分发 7,556（分发侧是脱敏骨架，只留 `PROFILE = "model-iot-v1"` 常量），而 `lifecycle.py` 分发侧反而更大（66,363 vs 54,016）。

代价已经付过：Windows 构建的 MLflow 制品路径反斜杠缺陷（公开 issue `learn-model-framework#11`）两仓各修一遍（私有 `f54db66`、分发 `91fae0d`）。而且血缘已经分叉——把 `runtime_contract.py` 整文件搬到分发仓会带进私有独有的 `OPTIONAL_START_STRATEGIES` 并让分发仓导入失败，所以只能**先修私有仓、再只搬差异**。

issue #48 给了三条路：①给 `distribute` 加逐文件工具链白名单的受控同步通道；②把分发仓 `model_lab/**` 降级为安装器/引导脚本；③保持手工同步，但把「应随分发仓发布」的工具链摘要登记在私有仓，随时可查差异。业主选定 ③。

## 决策

1. **只做可见性，不做同步。** 本轮明确不做 ① 与 ②：受控同步通道等于给公开仓开一条新的自动写路径（要连带定义白名单、冲突与回滚语义），降级为安装器会打断分发仓现有的自检、脚手架与 `setup` 用法。两者都超出"随时能看清漂在哪"所需，留作后续独立决策。
2. **可见性＝一条只读命令。** 新增 `model-lab toolchain-drift`（`model_lab/toolchain_sync.py`）：逐路径比较两仓摘要，输出四态清单（完全相同 / 内容不同 / 只在私有仓 / 只在分发仓）与「自基线以来变化」点名。
3. **比较面写死并公示。** `model_lab/**/*.py`、`model_lab_service_runtime/**/*.py`、`tests/**/*.py`、`scripts/*`、`pyproject.toml`；跳过 `.git`、`.venv*`、`__pycache__`、`node_modules`、`.ruff_cache` 与符号链接。`scripts/*` **不递归**——`scripts/取数探针/` 一类私有探针不进比较面。
4. **摘要用 utf8-lf 归一化**（`model_lab.document_loader.file_digest`）。两仓的换行检出策略不同（`.gitattributes`/`core.autocrlf`），按原始字节比较会把每次 Windows 检出都变成假漂移。
5. **基线登记在私有仓**：`docs/10-流程层/25-分发仓工具链同步基线.json`，由 `--write-baseline` 写入；首个基线登记于 2026-10-16T13:59:43+08:00，共 112 个路径（完全相同 9、内容不同 34、只在私有仓 52、只在分发仓 17）。命令**只写私有仓的基线文件，不写分发仓、不推送**。基线文件同时被显式排除在分发面之外（见决策 9）。
6. **默认不是门禁。** 不带旗标恒以退出码 0 结束，只报告；`--fail-on-drift` 才是退出码 1，且**目前没有任何门禁、CI 或钩子调用它**。这条刻意如此：可见性阶段先把事实摆出来，是否升级为门禁要单独决策。
7. **缺基线不等于干净，坏基线不静默。** 没有基线文件时报「基线尚未登记（不是没有变化）」并提示先登记；分发仓根目录不可读时退出码 4，绝不把"读不到"当成"无漂移"。
8. **变化必须点名方向。** 「自基线以来变化」逐条给出原因：私有仓新增 / 私有仓移除 / 分发仓新增 / 分发仓移除 / 只有私有仓变了 / 只有分发仓变了 / 两侧都变了 / 两侧都新增。只报"哪些不同"看不出"谁在动"。
9. **基线文件不进分发面。** `model_lab.distribution` 的 `_DEFAULT_EXPLICIT_EXCLUSIONS` 增加该基线路径。理由是这份文件是**私有仓记账**：它逐条列出只在私有仓存在的模块路径（`model_lab/gpu_publish.py`、`model_lab/verdict.py` 等）与两侧摘要，分发到公开仓既非本意也无用处。这是本决策对分发面的**唯一**改动——允许根（`docs/`、`models/`）与既有取舍一律不动。

## 影响

- **收益**：
  - 一条命令就能拿到两仓工具链的完整差异清单与自基线以来的变化，issue #48 的验收条件（"能一条命令输出差异清单"）落地；
  - 漂移从"靠人记得去看"变成**登记在私有仓、可复查、可 diff 的事实**，两仓各自修复仍走既有的「先修私有仓、再只搬差异」路径；
  - 换行差异被显式排除，避免了会掩盖真实漂移的假红。
- **约束与代价**：
  - **可见性不等于防漂移**：没人跑这条命令时漂移照样发生；基线只是快照，登记之后的变化要靠人重跑（或将来把它接进巡检/门禁）才看得见；
  - `online_acceptance.py` 这类**故意脱敏**的偏离会和真漂移混在同一张清单里，判断仍需人读（分发侧是骨架属有意为之，不是缺陷）；
  - 比较面一旦调整（例如扩到 `scripts/**`），必须与 `distribute` 的口径一起改，否则清单与实际分发面不一致。
- **边界**：
  - 不改变 `distribute` 的允许根与既有取舍（唯一改动是按决策 9 把本决策新增的基线文件显式排除），不写分发仓任何文件，不新增门禁调用点；
  - 不解决两仓血缘分裂本身（跨仓修缺陷要修两次的根因）——那是 issue #48 选项 ①/② 的范围，本轮明确不做；
  - 公开侧的指路口径仍在 `learn-model-framework#11`：权威源在私有仓，分发仓是剥离副本，修缺陷先修私有仓。
