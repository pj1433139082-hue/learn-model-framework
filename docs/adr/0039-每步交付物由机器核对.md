# 0039 每步交付物由机器核对

- 状态：已接受
- 日期：2026-10-17

## 背景

`docs/10-流程层/11-新模型开发SOP.md` 用文字规定了九步各自该产出什么，
`model_lab/workflows/model-lifecycle-v1.yaml` 也把阶段门禁写成了机器可读的检查，
但两件事都没解决「**这一步做完了没有**」：

- 门禁只在 `advance` 时整体判定，失败信息是「哪个门禁没过」，不是「这一步还缺什么、怎么补」；
- 门禁属于框架的推进动作，人（和智能体）在写文档、拉数据、出图的中间态里没有可用的核对反馈；
- 实际事故：模型讨论发生在仓库根，公式核对清单、问题汇总等产物直接落在仓库根，
  没有工作区、没有 `decisions.yaml` 的 ASK 闭环，事后只能靠人回忆「第几步没做完」。

## 决策

1. **新增只读核对能力 `model_lab/step_check.py` 与 CLI `model-lab step-check <工作区>`**：
   逐步骤列出「已产出 / 部分 / 缺失 + 补法」，退出码 `0`＝本阶段无缺项、`1`＝有缺项、`2`＝不是模型工作区；越界产物只在输出里单独提示，不并入退出码。
2. **判据只认已有事实源**：九步产出取 `docs/10-流程层/11-新模型开发SOP.md`，
   状态与决定项取 `model.yaml` / `decisions.yaml` / `model-spec.md` / `validation/`；
   段落判定与占位符判定复用 `model_lab.lifecycle` 的同一份实现（`_markdown_section` / `_PLACEHOLDER_TEXT`），
   **不得各写一套**，否则核对结论会与门禁结论互相矛盾。
3. **只核对「当前阶段正在产出的步骤」（前沿）**，已越过的步骤只列历史缺口、不判死：
   `draft`＝①②、`specified`＝③④⑤⑦、`built`＝⑥、`validated`＝⑧⑨、`released`＝⑨，
   与 `model-lifecycle-v1.yaml` 的门禁归属逐条对齐。理由：旧资产（已 `released` 的 09、
   维护型草稿）没有新模板的段落，追溯判死会制造永远无法清零的噪声。
   决定项缺席时同理：它本来要阻塞的那次转换已经发生，就按历史处理。
4. **仓库根不是产物的家**：核对同时报出仓库根的越界产物（白名单＝`RESIDENT_ROOT_FILES`，2026-10-20 起 8 项，见 ADR 0047）。
5. **交付通道是项目级 hook，而不是让人记得跑命令**：
   `step-check --write-context` 生成 `<仓库>/.dsh-hooks/context.md`，
   由本机 hooks-kit 插件的 `agent/pre-step` 在**每一轮用户输入前**注入（表头 `[hooks-kit …]`）；
   注入内容是纪律 + 进行中的工作区 + 前沿缺项 + 越界产物 + 核对命令，超限截断。
6. **最后一道是守卫**：`<仓库>/.dsh-hooks/settings.json` 用 `guard.workspaceRoot` 的路径策略
   拦下「在仓库根写模型产物」（根直接子级、文件名不在白名单、命中可疑后缀，如 `*.md` /
   `*.ipynb` / `*.csv` / `*.xlsx` / `*.pkl`），命中即拒绝并给出绕过方式。守卫不是判据，
   只是防止同一个错误再发生（2026-10-20 起 `guard.extraDeny` 正则已清空，见 ADR 0048）。
7. **不新造目录体系**：模型类产物仍然只进 `models/_drafts/<模型-id>/`；
   跨模型的流程说明进 `docs/10-流程层/`。核对能力不引入新的顶层目录。

## 后果

- 每个中间态都有可复现的核对结论（含 JSON 形态），可直接贴进回执或工作区；
- 门禁与核对共享判定实现，`step-check` 不会与 `advance` 结论冲突；
- hook 上下文每轮刷新，智能体不再依赖「记得看 SOP」；
- 新增维护面：`.dsh-hooks/context.md` 是产物，需在每步之后刷新（命令自带 `--write-context`）；
- 守卫只覆盖 `write` / `edit` 工具，`pwsh` 里的重定向写不在覆盖范围（守卫对命令只能看到字符串，无法区分读写），
  这一点必须写在文档里，不能假装覆盖完整。

## 被否决的方案

- **把九步检查塞进 `release-gate`**：门禁属于仓库级台账核对，跑一次要几十秒且面向「已存在资产」，
  不适合当作每步的即时反馈。
- **新写一套标记语言（在 `model-spec.md` 里插状态标记）**：会把「产物是否存在」变成「有没有写标记」，
  等于自己给自己发合格证。
- **让 hook 直接拒绝未完成步骤的写入**：核对的结论需要人判断（历史缺口、跨模型讨论），
  一律阻断会把正常讨论卡死；只在「产物落错地方」这种无歧义情形上用守卫拦。
- **把核对结论写进 `model.yaml`**：清单是模型契约，不是过程日志；过程结论属于 `validation/` 与核对输出。

## 修订

- 2026-10-17：步骤表改为从工作流 YAML 派生（[ADR 0041](0041-步骤表来自工作流的单一事实源.md)），
  `step_check` 不再硬编码九步；退出码口径收敛为「只反映本工作区」——仓库根越界单列 `root_ok`，
  只有 `--repo-wide`（CI）才把越界当阻断。
