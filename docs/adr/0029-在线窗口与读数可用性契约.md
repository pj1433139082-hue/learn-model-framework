# 在线窗口与读数可用性契约

状态：已接受（2026-10-13）

## 背景与决定

0.1.0 把 `target_date` 做成必填、只接受“已结束的整天”，并把窗口内出现非有限读数判为致命错误。现场按分钟调度、按天预测，平台既不保证传日期，也不可能为当天的请求等到次日；结果是同一条链路时而成功、时而报 `IoT value for ... is not finite`。

决定：数采测点模型在线契约改为三项。

1. **起始字段可省略**。起始字段（`target_date`）在开放日策略下不是必填；省略时按模型声明的时区取当天。平台请求签名据此把它标为 `required: false`，与公司部署模板“非必填项做平滑兜底（如 target_date 为空则取当前系统日期）”的约定一致。
2. **窗口可以是开放日**。策略 `target-date-to-now` 的窗口是 `[目标日当地零点, min(当前时刻, 次日零点))`；未来日期直接报错阻断；整日策略 `target-date-day` 的 24 小时校验保留。
3. **读数分“可用/不可用”**。某测点的可用读数 = 窗口内最后一个可解析且有限的读数；缺失、无法解析与非有限读数（±inf）一律按不可用处理，不再单独抛错。`mean` 聚合在某个声明测点整窗不可用时按可用测点求均值，全部不可用才阻断；`sum` 与单点绑定仍要求每个声明测点都有可用读数。

配套的两处证据口径：回执校验器对开放日窗口要求“响应不早于观察到的窗口终点”（整日窗口仍要求“请求发生在窗口关闭之后”）；`publish --apply` 要求回执钉在一个**已关闭**的整天上，因为远端复算必须与本地证据在 1e-6 内一致，而复用当天开放窗口会随取数时刻漂移（曾在 Run `bdbf35e8883441558295ce91cfaa51eb` 上实测 `remote_prediction_mismatch`）。

## 边界

- 值域校验仍然不做：运行时只保证“可解析且有限”，量程与哨兵值属于观测与告警，不进入在线阻断，也不得靠放宽契约掩盖坏数据。
- 不使用前向/后向填充：`mean` 容差只针对“声明的测点在窗口内没有可用读数”，不把窗口之前的历史读数、也不把未来样本搬进窗口。
- 开放日策略下每次推理的窗口终点不同，因此**不可能**用同一个回执复核两次运行；发布证据必须用整日窗口，日常调度用开放日窗口。

## 后果

现场按分钟调度、按天预测可以稳定出数；同一模型在不同时刻得到的窗口不同，结果不再逐位可比，可追溯性由“每次发布的整日回执 + 归档快照”承担。读到 `not finite` 报错的历史记录时，应知道那是 0.1.0 的行为，0.2.0 起该报错不再存在。
