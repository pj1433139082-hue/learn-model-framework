# 06-模型任务问答与交互档位

本页是智能体协作的**提问规则**，不是另一套模型生命周期。先判断用户要做什么，
再决定是否需要提问；`model-lab` 的 `status`、`decisions.yaml`、`--apply` 和门禁
仍决定能否推进。不要把 `ASK`、`CONFIRM`、`AUTHORIZE` 当成三个交互档位。

## 一次选档

新的**可写模型任务**开始时，智能体在首次回复中说明识别出的任务类型，并给
使用者一次选择机会：

> 这次按哪种方式协作？① 全自动：本地步骤连续执行，只在必填业务决定或远端
> 授权处停下；② 半自动（推荐）：本地步骤自动执行，业务决定集中一轮确认；
> ③ 逐步确认：每次关键本地写入、构建或状态推进前看计划。回复编号或名称即可。

用户已指定档位，或回复“按推荐”“采用默认值”，就直接采用相应档位，不再
重问。没有选档答复时按推荐的半自动继续已交办任务，**不为选档新增一道
授权门禁**；沉默绝不意味着全自动。纯只读查询、诊断、进度报告不弹选档。
智能体在本次任务的工作计划中记录场景、用户选择或默认采用的档位及其变化。
续办同一任务先查该记录；已有记录不重问，用户随时可改档。档位只控制
交互频率，不是永久许可，不写入 `model.yaml` 或
`decisions.yaml`。三档的硬门禁与远端授权边界见 ADR 0014。

## 按需求分流提问

下表的“问”只指**证据里没有、且本阶段确实影响下一步的业务选择**。先从
目标模型、发布快照、测试及数据中取事实；不要为了填模板向用户求证可计算
的版本、摘要、指标、测点统计或路径。一个任务同时涉及多场景时，先问阻塞
上游工作的选择，下游问题在证据出现后再问。

| 用户需求 | 自动查或做 | 需要问的情形 | 本轮不问 |
|---|---|---|---|
| 查原因、查进度、看数据（只读） | 查状态、日志、数据质量和证据，说明已证实与待证实 | 目标无法定位、数据源不可访问且没有可替代证据时，仅问定位信息 | 交互档位、本地执行授权、已能算出的事实 |
| 从零创建模型 | 读需求资料，生成候选输入输出、公式、异常处理和验收建议 | 用途/范围、缺失的契约字段、真实业务口径和验收取舍；同一依赖层合并问 | Python 3.11、模板目录、自动可查的环境信息 |
| 已发布模型的行为不变修复或 3.11 迁移 | 查父版签名、行为基线、依赖，建独立维护版并验证等价 | 旧行为无可信基线、线上契约不明或修复会改变业务行为时，问冲突处置 | 重问已确认的公式、输入名称、负责人和发布历史 |
| 改公式、阈值、数采点、时窗或输入输出契约 | 对比父版与拟议新版，单列差异并建立新语义版本 | 只问发生变化的字段、异常策略、验收口径及控制动作 | 重新审问没有变化且有证据的旧字段 |
| 数据审查与测点映射 | 自行取数、统计缺失/异常、核对设施设备信号和单位 | 事实导致剔除、补值、改映射或放宽物理边界等业务取舍时 | 让用户手算缺失率或代查已有点位资料 |
| 构建、测试、验收 | 自动构建、运行测试、计算指标和差异，给出可复现证据 | 结果偏离已同意口径、需要在有意义的方案间取舍，或必须冻结验收结论时 | 每条测试命令的执行许可、可自动计算的指标 |
| 生成发布包或上传 | 自动核验 Python、MLflow 签名、制品和目标配置 | 平台实验名/模型编号、发布作者/账号标识缺失时才问；真实上传须有目标与内容明确的用户指令 | 让用户提供可自动查的 ABI、摘要、目标；不重复问已给的编号和账号 |
| 公司业务平台人工任务调用 | 仅在用户要求该集成链路时核对平台绑定和调用回执 | 缺少平台任务的实际业务输入或操作范围时 | 把这项测试当成 MLflow 上传或本地发布快照的门禁 |
| 生产调度、监控或回滚变更 | 展示拟操作及回退计划 | 具体生产行为、受影响范围和没有答案的业务决定 | 把“上传”自动扩大为调度或控制动作 |

## 一轮问题怎么问

先运行适用的只读检查，读取当前门禁和已有答案；只提出这一轮**相互独立**
的开放问题。每题写清楚证据、影响、推荐选项与其他选项；同一轮编号列出，
允许用户用一次“全部按推荐”回答这一轮。将每一项完整答案写入对应
`decisions.yaml`，不能存“按推荐”四个字，也不能把未展示的后续问题视作
获答。依赖数据实测或构建结果的问题等结果出现后再问，不预先假设通过。

用户的一个明确回答覆盖**已展示且目标、范围、推荐内容未变**的一组问题；
续办、状态推进、下一条本地命令都不得重复索要同一答案。只有新证据推翻了
原前提、模型/合同/文件范围变化，或要执行新的远端事务，才重新说明差异并
提问。缺口确实存在时只报一次具体阻塞及下一步；不能用重复授权问题掩盖
禁用的发布后端。用户已明确要求上传指定模型版本到指定实验时，这条请求就是
该次上传的指令，不再追加一次形式化“确认上传”；推送 Git、合并分支或生产
调度仍是不同操作，不从上传指令中推定。

### 问题必须交到使用者面前

若当前门禁因必填 `ASK`/`CONFIRM` 阻塞，智能体须在交还控制权之前主动给出
这一轮的编号问题、推荐答案和可选的不同答法。**先在可见消息中给出同一组
简洁选项，再尝试发送结构化选择框**；工具返回“已发送”只证明发起了请求，
不证明人看到了控件，不能只说“见弹窗”。如果到本轮结束仍未收到答复，最终回复也要
完整重述问题，不能只说“等你回答刚才弹出的框”。没有选项控件时直接用文字
提问，用户回复编号、改动意见或“全部按推荐”均可。**这只是同一轮问题的
显示兜底，不是重复征求批准。**

收到答复后，仅将已展示且被回答的决定记为 `confirmed`，保存完整答案和
确认时间；随后自动重跑 `status` 并执行任务范围内已获准的本地推进。不得
再就写入 `decisions.yaml`、`advance --apply` 或同一方案另开许可问题。若下
一阶段出现依赖新证据的不同业务决定，才发新一轮问题。真实平台上传仍受已实现
适配器、实包验收、网络可达性与限定事务边界约束；它们不是公司二次审批。
上传后的结论须区分“MLflow 发布成功”“公司业务平台调用未验证”和
“本地发布快照尚未归档”。一次性演示已确认不调度时，不以未启用调度为
阻塞，也不为同一运行方式再开 `operations-plan` 问题；详见
[ADR 0017](../adr/0017-发布验收与运营边界分离.md)。
