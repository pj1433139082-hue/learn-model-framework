# 人工操作快速开始

日常使用本仓库的 `main`；真实资产在外部私有模型目录。本机配置、技能生成目录和环境不会跟随 Git 克隆。

## 一次初始化

Windows 推荐在框架目录运行 `& .\scripts\bootstrap.ps1 -ModelsRoot "D:\private-models"`，Linux 运行 `bash scripts/bootstrap.sh --models-root /path/to/private-models`。初始化只检测环境、安装框架依赖、保存本机目录和同步项目技能，不取真实数据、不上传模型。缺项会给出实际下一步，不需要重新批准已交办的本地任务。

安装依赖需要访问公网。使用本机 HTTP 代理时，先在当前终端设置 `HTTP_PROXY`、`HTTPS_PROXY` 为自己的代理地址；助手和手工安装命令继承这些变量，不改变系统代理、VPN 或内网路由。例如 PowerShell 用 `$env:HTTPS_PROXY = "<你的HTTP代理地址>"` 和 `$env:HTTP_PROXY = $env:HTTPS_PROXY`；Bash 用 `export HTTPS_PROXY='<你的HTTP代理地址>' HTTP_PROXY='<你的HTTP代理地址>'`。无需代理则不设置，不把个人端口或凭据提交到仓库。

## 手工后备

安装了系统 Python 3.11 的 Windows 机器，可在框架目录执行：

```powershell
py -3.11 -m venv .venv-311
& .\.venv-311\Scripts\python.exe -I -m pip install -e ".[test]"
& .\.venv-311\Scripts\python.exe -I -m model_lab setup --models-root "D:\private-models" --apply
& .\scripts\model-lab.ps1 doctor
```

已有 `.venv-311` 时先核对解释器，再复用它；不要用 3.12。Linux 对应 `python3.11 -m venv .venv-311` 和 `.venv-311/bin/python -I -m pip ...`。也可以使用 `uv venv --python 3.11 .venv-311`、`uv pip install --python <该解释器> -e '.[test]'`。

无需激活环境即可使用统一入口：Windows `& <框架路径>\scripts\model-lab.ps1 <命令>`；Linux `bash <框架路径>/scripts/model-lab.sh <命令>`。直接使用解释器时保留 `-I -m model_lab`，并明确传入私有工作区。不要在带旧 `model_lab/` 副本的目录用未隔离的 `python -m model_lab`。

## 项目技能与 hook

Skillshare 已安装时，在框架目录执行：

```powershell
skillshare sync --project --dry-run --json
skillshare sync --project --json
skillshare audit -p --format json --no-tui --yes
```

只维护 `.skillshare/skills/`，同步目标是本项目 `.agents/skills/`。初始化会检测技能是否与源码一致；更新源码后需要重新同步，并让客户端重新加载技能。命令不在 PATH 时可使用已核实的完整安装路径。未安装 Skillshare 时，直接读取 `.skillshare/skills/model-lab-router/SKILL.md` 及其最小技能文件，勿手工复制到全局技能目录。

仓库交付 `.codex/hooks.json`。在支持该 hook 的客户端中审核并信任配置；初始化无法证明客户端已信任它。未启用时仍用 `AGENTS.md`、入口页和 `context/status` 完整恢复，不增加模型门禁。

## 更新与回退

在本仓库 `main` 上先 `git pull --ff-only`，再运行 Windows `& .\scripts\bootstrap.ps1 -Update` 或 Linux `bash scripts/bootstrap.sh --update`。已保存的模型目录会被复用；依赖、技能和来源记录随更新检查。`doctor` 输出实际模块位置、框架版本和提交，`.model-lab/setup-state.json` 保存更新前后来源。

回退时保留现有目录与所有真实模型，另建克隆：

```powershell
git clone <仓库地址> learn-model-framework-recovery
cd learn-model-framework-recovery
git switch --detach <setup-state 中记录的旧提交>
```

然后按该提交自带说明配置环境，指向原外部私有模型目录。旧提交若没有初始化脚本，使用 Python 3.11 手工安装并设置 `MODEL_LAB_MODELS_ROOT`；不要把新脚本复制进旧版本假装同一环境。工具回退不等于模型回滚；已发布 Run 和版本处置按具体任务执行。

## 任务续办

对已有私有模型执行 `context <工作区>` 与 `status <工作区>`；文档位置以输出的实际框架指针为准。记录一次已选择的档位与下一步：

```powershell
& .\scripts\model-lab.ps1 task-plan "D:\private-models\_drafts\example-flow" --task-id example-maintenance --mode assisted --intent maintain --next-action "检查现有行为基线" --apply
& .\scripts\model-lab.ps1 task-plan "D:\private-models\_drafts\example-flow" --task-id example-maintenance
```

任务计划保存于该私有工作区 `.model-lab/tasks/`；不记录永久发布许可或凭据。`workflow-state.json` 仍由模型事实生成；任务计划不代替业务决定、阶段门禁或实时平台状态。纯框架任务的计划和验收使用框架评审记录，不需要虚构一个模型 ID。

当前能力：新模型支持 CPU-IoT、GPU、Chronos 的契约模板，构建与真实上传仍以已实现的 CPU-IoT 适配器为准。`maintain` 目前不能自动安全分叉已发布测点 `serving` 版本，GPU/Chronos 也需专用构建路径；遇到这些场景应报告未实现的能力并保留父版本，不能绕过校验或当作已经支持。
