# 在役模型维护版必须安全分叉

状态：已接受（2026-09-26）

后续修订（2026-10-10）：澄清"改写 released 资产"的边界。修改 `model.yaml` 中 `source.entrypoint`、`source.notebook`、`source.documentation` 的**相对路径字段**，在被指向文件的内容与 SHA-256 摘要均不变的前提下，属于位置调整而非资产改写，不构成新的维护版本，也不需要安全分叉；模型身份、契约、版本、行为与发布记录任一发生变化时，本决策的原要求完整适用。见 [ADR 0020](./0020-历史审计证据由归档分支保存.md)。

后续修订（2026-10-10，血缘口径）：上一条的判定现已由机器口径落实。维护草稿的血缘摘要显式排除 `source` 段的三个引用路径字段与 `model.maintenance_status`，因此只改路径不再让既有草稿失配；对应的 `*_sha256` 摘要字段不在排除之列，清单里登记的摘要值一改，血缘立即失效。但要说清机器核验到哪一步：按 [ADR 0020](./0020-历史审计证据由归档分支保存.md)，`entrypoint_sha256` 与 `notebook_sha256` 属仅登记、不读磁盘，所以本修订所要求的"内容与摘要不变"这一前提，对部署入口与 Notebook 只能靠人工核对与归档分支保证，机器能核验的只有 `documentation_sha256`。排除清单而非白名单，清单新增字段默认被钉住。见 [ADR 0007](./0007-现有模型作为在役资产持续留档.md) 的血缘口径修订。

## 决策

当前八个已发布 CPU-IoT 模型的 Python 3.11 行为不变迁移，用
`model-lab maintain <在役模型目录> --version <新补丁版本>` 预览，并在已交办
的本地任务中显式 `--apply`。命令在 `models/_drafts/<model-id>-<version>/`
创建新工作区，保留同一模型 ID、已发布输入输出契约与可用的旧行为基线；运行
环境改为 Linux x86_64 / Python 3.11。旧模型目录、源码、Notebook、制品
引用、Run 和发布快照均不覆盖，新工作区不继承旧平台 Run 或旧制品作为新成果。

维护元数据记录父模型目录、当前版本、父清单和发布快照按 UTF-8/LF 规范化后的 SHA-256，以及
`behavior_policy: unchanged`。`status` 和全库 `release-gate` 复验父子关系；
同一已发布父版本最多可并存一份行为不变补丁草稿与一份另立次版本的在线契约升级草稿；
各自的模板、版本规则、父版摘要和血缘均须独立校验。一般 `new` 仍拒绝重复 ID，
父版本被改写、维护元数据缺失、同类第二份草稿或额外普通草稿均失败。
维护工作区从 `draft` 走到 `releasable`，不会自动替换父版本或成为
`released`。

测点编码数组和历史时间窗口会改变平台输入签名，必须使用
`maintain --change-kind contract-upgrade --version <下一次版本>.0`，不能算补丁。
契约升级保留父版固定输入基线的原始文件作为留档，但不把它误用作新契约的
可执行基线；新版本需要重新构建并核验基线。`draft → specified` 要求明确的
测点绑定、时间口径与 `source-history-v1` 历史特征适配，线上取数失败不退回
mock。具体模型仍须验证特征重采样与父版实际行为一致。

现有维护入口只支持这八个 CPU-IoT 资产。GPU/Chronos 的显存、CUDA 与原生
制品合同不能从 CPU 模板猜测；未来要复用此入口，应先补相应测试和目标适配。
此决策不启用公司平台发布后端；真实上传、回载、快照固化和在役替换仍需单独
实现与明确的限定事务授权。
