# 框架使用与升级评审

日期：2026-10-01。评审基点：`6e27c2d`。状态：用户已答复 Q1/Q2，按本轮边界实现并验证；本文不是具体模型的部署验收。

## 已确认的边界

- 通用框架以本仓库为维护源；真实模型、测点、数据、公司包与发布回执保存在仓库外私有目录。
- 正式训练、构建和部署使用 Python 3.11。
- 交互档位按任务恢复，已明确交办的本地步骤自动执行；只询问尚未解决的业务选择。指定模型的上传指令不应再次被包装为同一次上传的确认题。
- `model.yaml`、决策与模型证据是事实源；生成状态 JSON 和只读 hook 帮助恢复，不替代事实核对。

## 事实与缺口（评审基点）

以下记录 `6e27c2d` 的状况，不代表本轮修复后的现状；当前实现与验收范围见文末及同日期验收记录。

### 1. 运行目录可能使新解释器加载旧框架

已实测：从仍包含旧 `model_lab/` 副本的私有备份工作区运行新框架的 `python -m model_lab`，Python 会优先加载当前目录的旧模块。仅换解释器不能证明已经换框架。新框架解释器的隔离模式和新框架的 console-script 入口可避开本次复现的当前目录遮蔽。

评审基点的 `model_lab/__init__.py` 版本为 `0.1.0`；旧副本同样报此版本，基点 `doctor` 没有展示实际加载的模块位置与框架提交。建议提供固定入口并报告解释器、框架来源与版本；不要以版本字符串相同推断两份代码相同。

`context` 目前输出框架内相对文档路径，未指出框架根目录。在外部模型目录调用时，智能体可能从私有目录寻找不存在的 `docs/`。建议在输出中明确框架根目录，并提供可定位的文档指针。

### 2. 干净克隆后的技能与 hook 配置说明不完整

`AGENTS.md` 要求使用项目路由技能，但 `.agents/skills/` 是忽略的生成目录。README 只说明 Python 环境和模型目录，没有给出 Skillshare 同步、更新后再同步及核对结果的完整步骤。建议补上可直接执行的说明与直接读取技能源文件的后备路径。

README 创建虚拟环境后没有激活，却在后续步骤使用裸 `model-lab` 命令；干净终端未必能找到安装在虚拟环境中的入口。建议使用统一的明确路径入口，或补齐激活与重开终端后的说明，不依赖机器上碰巧已有的全局命令。

hook 的只读后备入口已有说明；首次使用仍应能看见 hook 是否可用，并给出当前客户端适用的信任/启用指导。hook 未启用时不增加生命周期阻塞。

### 3. 公司能力诊断仍沿用旧布局

`model_lab/repository_doctor.py` 从框架仓库内 `framework/` 检查公司模块与原生运行时；实际共享框架要求公司包在外部私有目录，构建也接受外部 ZIP。当前 `doctor` 可正确报告基础框架可用，但公司能力标志无法反映这条外部路径。

建议按实际私有配置检查包与目标 OS/架构，或明确标记该项尚未检查；保留“本地框架可用”“目标运行时适配”“公司网络可达”“具体模型验收”各自的结果，避免缺哪项就让用户重新批准哪项。

### 4. 私有扩展有协议，缺少首次接入的完整示例

框架通过 `model_lab.baseline_runners` entry point 接入私有基线，通过 `MODEL_LAB_PRIVATE_TEST_MODULE` 接入模型测试。共享库保留通用协议与合成检查，但既有模型不能仅凭这两条配置名就完成迁移。

建议交付完全虚构的私有扩展示例、安装与兼容步骤，验证外部模型目录、独立预期结果、真实测试回执之间的衔接。具体真实模型在其私有工作区验收，不能把合成示例通过当成部署完成。

### 5. 更新与续办需要更具体的记录方式

当前入口说明了任务恢复，路由技能要求从任务工作计划恢复交互档位，但没有统一的工作计划位置和最小字段约定。hook 的会话缓存保存模型焦点与歧义提示，不保存完整任务进度。

建议为任务记录已选档位、下一步、待回答业务问题和已有证据指针；不复制模型事实，也不保存永久远端授权。框架更新还需明确当前来源、版本、依赖同步、技能同步、兼容检查与回退步骤。公开框架内不保存真实模型的这类记录。

### 6. 隐私检查需要覆盖真正准备提交的内容

已在自动清理的合成 Git 仓库复现：暂存 README 含虚构的凭据形状标记，而工作区 README 为安全文本时，`release-gate` 错误返回通过；提交暂存内容后才报历史内容错误。`_tracked_paths` 从 Git 暂存区列出文件，却从工作区读取内容，完整历史扫描不能在提交前补足这一缺口。建议分别检查暂存对象与工作区，并以纯合成资料回归这类差异。若匹配现有规则，提交后的 CI 可以发现此类问题，但不等于本机提交前已检查正确。

基点共享源码中的检查规则保留特定公司域名和特定私有基线类型的字面量。它们不是模型数据集，但与纯通用模板的目标不够一致；本轮删除当前源码中的这些字面量，保留通用形状检查，不扩大实现为新的私有规则加载器。当前源码修复不会抹掉旧提交中的内容；已有历史的处置须单独评估，本文不授权历史重写、删除或强推。

实现阶段的独立对抗审查另复现了合并新增后再重命名的历史路径漏检，已使用禁用重命名检测、展开合并和根提交的历史清单补齐；合成回归验证最终暂存区/工作区可通过，而历史仍能拒绝曾出现的私有路径。

### 7. 外部目录契约与维护入口存在旧约束

README 允许私有目录使用任意名称，`new` 也在该目录的 `_drafts/` 创建草稿；`maintain` 和 `draft-fork` 却要求根目录字面名称为 `models`。按 README 的目录示例开始，后续维护入口可能在读取模型内容前就被拒绝。建议统一外部根目录规则，按明确配置与结构判断，不依赖目录字面名称。

维护入口目前还拒绝含 `serving` 的发布模型，说明已发布测点模型后续安全分叉需要补齐支持或明确替代入口。不能把通用模板可创建描述为所有已发布版本均可维护。各写入命令应统一检查工作区位于框架外；当前这一检查主要用于 `new` 和 `context --all`，不能靠用户始终选对路径来保持共享仓库边界。

## 本轮已确认

Q1：采用推荐的一次本机初始化助手与手工后备。用户只指定私有模型目录；助手检测 Python 3.11、框架来源、项目技能和 hook 文件，不替用户信任客户端配置。`setup` 默认预览；明确运行 bootstrap 即执行本机初始化，不增加二次审批。

Q2：用户明确选择同事直接使用 `main`，覆盖早先的稳定标签建议。更新执行 `git pull --ff-only` 后 bootstrap update，同步依赖和技能并记录前后提交。具体模型任务保留所用框架版本/提交及修改状态；更新不自动迁移模型业务契约、算法或验收证据。失败时另建旧提交克隆恢复工具，保留原模型。

上述决定记录在 ADR 0018。首次配置、升级或能力检查只处理实际使用场景，不给所有模型增加统一的额外发布确认。

## 实现与验收范围

从全新克隆开始，由无项目上下文的子智能体只按入口与使用说明操作：先完成虚构模型的初始化、创建与状态恢复，再测试从含同名旧模块的目录调用新框架、拉取框架更新及恢复原版本。分别记录框架层结果与私有模型/公司服务尚未验收的范围。

本轮新增本机初始化与隔离启动器、任务计划、绝对文档指针、外部 ZIP 静态诊断、外部目录写入检查，并修复暂存对象与工作区分离扫描。技能来源和入口已对齐。初始化配置及更新记录始终在忽略目录内；模型任务计划在外部私有工作区内，不保存永久上传授权。

验收结果另见同日期验收记录。已发布测点 `serving` 版本的自动维护分叉和 GPU/Chronos 专用构建不在本轮扩展范围，入口已明确说明。没有修改旧私人备份仓库、重写历史、安装公司包、执行真实取数或上传模型；没有推送或合并。
