# 0058 工作流选择单一来源：workflow.id 优先，模板表只作回退

> 本 ADR 保留私有源仓原文；`step-check`、`ledger`、`.dsh-hooks` 在本公开框架分发仓未实现，请以 `status`、`context`、`.codex/hooks.json` 为准。

- 状态：已接受
- 日期：2026-10-21

## 背景

"这个工作区该走哪条工作流"此前有**两处各自独立的判断**：

1. `model_lab/step_plan.py:438` 的 `workflow_for_workspace()`：读 `model-lab.yaml` 的
   `workflow.id`，`plan_for_workspace()` 与 `step-check` 的步骤表都基于它；
2. `model_lab/lifecycle.py` 的 `_workspace_report`（改动前 :853-864）：**完全忽略**
   `workflow.id`，只按 `template.id` 做 if/elif 推断——`maintenance-model` 判维护流程、
   `contract-upgrade-model` 判契约升级流程，其余一律主流程。

真实的 `model-lab.yaml` 同时写着两个字段，例如 `template.id: contract-upgrade-model` 与
`workflow.id: contract-upgrade-lifecycle-v1`；模板与工作流也允许不同名（`TEMPLATE_WORKFLOWS`
里 `draft-contract-upgrade-model` 指向主流程，见 `step_plan.py:35-40`）。两处一旦冲突，
同一个工作区会各判一条工作流：`step-check` 按声明的 `workflow.id` 列步骤与交付物，
而 `advance` 依据的 `_workspace_report` 按模板推断给门禁——"第 1 步已过"与"生命周期门禁
要求另一套段落"可以同时成立，结论取决于先跑哪个子命令，而不是工作区写了什么。

历史资产（01–08，没有 `model-lab.yaml`）没有声明，但也必须有确定的默认值。

## 决策

1. **`workflow.id` 是工作流选择的唯一事实源**：新增
   `_workflow_id_for_workspace(workspace: Path) -> str`（`lifecycle.py:838`），
   首选调用 `model_lab.step_plan.workflow_for_workspace(workspace)`。
2. **声明优先于模板**：返回值非空即采信，不再读取 `template.id` 做推断。
3. **历史资产用主流程**：返回空串（`LEGACY_WORKFLOW`，即没有 `model-lab.yaml`）时用
   `WORKFLOW_ID`。
4. **模板表只作回退**：`workflow_for_workspace` 抛 `StepPlanError`（缺 `workflow` 段 /
   缺 `workflow.id`），或读取文件失败（`OSError` / `UnicodeError` / `yaml.YAMLError` /
   `RecursionError`）时，才回退到 `TEMPLATE_WORKFLOWS.get(template.id, WORKFLOW_ID)`；
   模板 id 不认识时仍落到主流程。
5. **保留原有保护**：`model-lab.yaml` 是链接或 junction 时不解析，直接按主流程处理
   （与改动前一致：链接的 metadata 不作为工作流依据）。
6. **`_workspace_report` 只调这一个函数**（`lifecycle.py:880-881`），删除原来的
   `if/elif template.id` 推断；门禁文档仍由 `_workflow_document(workflow_id)` 加载，
   非法工作流 id 仍报 `workflow_invalid`。

## 后果

- `lifecycle` 的状态机门禁与 `step_plan` 的步骤表同判：对任一工作区，
  `workflow_for_workspace(dir)` 与 `_workflow_id_for_workspace(dir)` 必须相等。
  全仓核对 16 个含 `model-lab.yaml` 的工作区（8 个契约升级、8 个主流程），0 不一致。
- 历史资产仍默认主流程；模板表漂移只会影响"有 `model-lab.yaml` 但缺 `workflow` 段"的旧工作区，
  影响面收窄到真正的残缺声明。
- 模板与工作流不同名的工作区（`template: maintenance-model` + `workflow: model-lifecycle-v1`）
  现在按声明走；`scaffold-metadata-valid` 门禁仍会把双字段不一致报出来
  （`lifecycle.py:539-569`，既有检查，不是本次新增的限制）。
- 新增模板时只改 `TEMPLATE_WORKFLOWS`（`step_plan.py:35-40`）一处；`lifecycle` 不再有第二张表。
- **已知限制**：
  - 回退路径会再读一遍 `model-lab.yaml`（`workflow_for_workspace` 已经读过一次），
    本地文件可忽略；如将来有远程工作区再考虑合并读取。
  - `_workflow_document` 只接受三个工作流 id；`workflow.id` 声明了未知工作流时
    `lifecycle` 报 `workflow_invalid`，`step_plan` 报 `workflow_unsupported`，
    两处错误码措辞尚未统一（本次只收敛选择来源，不改错误码）。
- 测试落点：`tests/test_step_plan.py` 的 `LifecycleWorkflowSelectionTests`（声明优先、模板回退、
  无 `model-lab.yaml` 用主流程、模板表逐项回退、未知模板落主流程）与
  `tests/test_lifecycle.py` 的 `WorkflowSelectionSingleSourceTests`（真实 `models/_drafts`
  工作区与 `step_plan` 一致；`workspace_status` 确实把声明的工作流交给 `_workflow_document`）。

## 被否决的方案

- **继续按 `template.id` 推断**：双字段冲突时永远无法判断以谁为准；而且
  `draft-contract-upgrade-model → model-lifecycle-v1` 这类"模板与工作流不同名"的表项
  会让推断必然猜错，只能靠再抄一份表补丁。
- **两处都读、取交集（或先比一致再选）**：多出一层"谁赢"的规则；对缺 `workflow` 段的历史工作区
  会直接全挂，最后仍要回退，事实源没有减少。
- **让 `lifecycle` 自己再实现一份工作流判定**：同一逻辑两份副本，正是 ADR 0041 之后要消掉的问题；
  两处对同一工作区的答案会再次漂移。
- **改 `model-lab.yaml` 只保留 `workflow.id`、删掉 `template.id`**：脚手架、报告与升级流程
  多处按 `template.id` 找模板，属于脚手架契约变更，超出"工作流选择单一来源"的范围。
