# 0050 私有模型根限定在本仓库 models

- 状态：已接受
- 日期：2026-10-20

## 背景

从公开框架仓分离之后，`setup --models-root` 一直要求「仓库外的私有模型根」，可三处口径互相打架：
文档写「必须指到仓库以外」，`model_lab/environment.py` 的 `_ensure_outside_framework()` 只拒绝
`models` 本身、放行 `models/_drafts` 这类子目录，`model-lab/distribution.py` 的提示又写 `--models-root models`
（当时必败）。结果是新机器上没人能一次配对：按文档指到仓库外能过，按命令提示指 `models` 必被拒。

事实是本仓库就是私有仓：在役资产在 `models/0X_<平台名>/`、未发布工作区在 `models/_drafts/`（本决策作出时是 9 个资产、23 个工作区；2026-10-20 归档与退役之后为 11 个资产、10 个工作区）；
维护通道也早就按这个结构写死——`model_lab/maintenance.py:235-253` 与 `model_lab/draft_upgrade.py:204-205`
都要求 `<root>/_drafts` 存在、且 root 的目录名就是 `models`。
2026-10-20 用户拍板：**私有模型根不能写在仓库外**。

## 决策

1. **唯一合法根是本仓库内的 `models` 目录**，标准写法 `--models-root models`；本机设置、环境变量同受此约束。
2. **三条拒绝**（`model_lab/environment.py` 的 `_ensure_repository_models_root()`）：
   1. 落在仓库外 → `models_root_outside_framework`；
   2. 在仓库内但目录名不是 `models`（含 `models/_drafts` 这类嵌套根）→ `models_root_not_models_directory`；
   3. 存在但不是目录 → `models_root_not_a_directory`。
   第 2 条同时挡住「再套一层」：否则 `<root>/_drafts` 会变成 `_drafts/_drafts`，`new`／`draft-fork`／`archive-release` 全部失效。
3. **机器侧只有一处实现**：`configured_models_root()`（优先级 命令行 > `MODEL_LAB_MODELS_ROOT` > `.model-lab.local.json`）
   与 `read_local_settings()` 共用同一个校验函数；旧本机设置里的外部路径再读出来即 `local_settings_invalid`。
4. **`.model-lab.local.json` 仍被 Git 忽略**，`setup --apply` 写入绝对路径；换机器重跑 `setup --models-root models --apply` 即可。

## 后果

- 正面：文档、代码、命令提示三处口径统一；`scripts/bootstrap.ps1 -ModelsRoot models` 可以一次跑通；
  草稿与在役资产同根，`archive-release <工作区> --target-name <NN_名称>` 的目标路径可直接推导。
- 代价：曾经配过仓库外根的机器必须重跑 `setup --apply`；`ensure_external_workspace()` 的语义没有变，
  它继续用于 `task-plan` 的工作区校验与公司 IoT ZIP 的落点校验（那两类本来就该在仓库外或允许仓库内子目录）。
- 验证：`tests/test_environment.py` 覆盖「接受 `models`／拒绝仓库外／拒绝错名／本地设置越界」四条断言，
  `tests/test_setup_cli.py` 覆盖 CLI 两种拒绝码与 `--apply` 写回的绝对路径。

## 被否决的方案

- **保留「仓库外」，只改文档**：与用户口径直接冲突，且与私有仓结构不符。
- **允许 `models/_drafts` 作根**：草稿会落进 `_drafts/_drafts`，维护通道与 `draft-fork` 的父目录断言立即失效。
- **只校验「在仓库内」不校验目录名**：允许出现多个模型根，`<root>/_drafts` 的语义随之漂移，归档时无法从配置推导目标目录。
