# 0041 步骤表来自工作流的单一事实源

- 状态：已接受
- 日期：2026-10-17

## 背景

`step-check` 最初把九步写死在 `model_lab/step_check.py`（`STEP_SPECS` / `STEP_STAGE` / `FRONTIER_STEPS`），
而生命周期门禁早就由 `model_lab/workflows/*.yaml` 声明。同一件事实（第几步、属于哪个阶段、要哪些段落、
什么时候算前沿）因此有两份实现：改工作流 YAML 不会影响 `step-check`，新增一条工作流（维护、在线契约升级）
`step-check` 完全不知道，只能按主流程兜底，报出一堆不存在的缺口。

## 决策

1. **步骤表从工作流 YAML 派生**（`model_lab/step_plan.py`）：`step_plan(workflow)` 把 `states[].gates[]`
   里的段落门禁映射成「第几步、属于哪个状态、要哪些段落、要哪些交付物」，代码里不再手写步骤数组。
   工作流支持 `model-lifecycle-v1`（九步）、`maintenance-lifecycle-v1`（八步）、
   `contract-upgrade-lifecycle-v1`（八步）。
2. **交付物由步骤声明**：`step_plan` 给每步挂 `artifacts`（`inputs` / `questions` / `serving` / `plots` /
   `bindings` / `validation-evidence` / `model-tests` / `baseline` / `history-feature-adapter` / `notebook` /
   `publication-receipt`），`step_check` 只做通用核对器（文件在不在、证据全不全），不为某一步写专用逻辑。
3. **前沿由门禁派生**：有门禁的状态入口才算「当前正在产出」（`draft`→①②、`specified`→③④⑤⑦、`built`→⑥、
   `validated`→⑧）；没有门禁的状态（维护与在线契约升级的 `released`）沿用最近一个有门禁阶段的步骤。
4. **模板→工作流映射只有一张表**（`TEMPLATE_WORKFLOWS`）：生命周期门禁（`_gate_scaffold_metadata_valid`）
   与 `step_plan` 共用，草案升级模板 `draft-contract-upgrade-model` 也钉在这张表里。
5. **历史资产兜底**：没有 `model-lab.yaml` 的工作区按主流程核对，且 `released` 的运营资料步只提示不阻断
   （旧资产没有新模板的段落，追溯判死会制造无法清零的噪声）。
6. **仓库根越界与工作区无关**：`WorkspaceCheck.ok` 只判工作区自身的缺项，越界产物单列 `root_ok`；
   命令退出码只反映本工作区，`--repo-wide`（CI）才把越界当阻断。

## 后果

- 新增或修改工作流只需改 YAML，`step-check`、hook 上下文、CLI 一起跟上，不会出现两份步骤表；
- 维护与在线契约升级工作区不再被按主流程误判（此前会报「缺第 8 步运营资料」之类的假缺口）；
- 段落与交付物的口径集中在 `step_plan`，`step_check` 变成薄核对器，新增交付物只改一处；
- 代价：派生规则本身需要测试兜住（`tests/test_step_plan.py`），工作流 YAML 的段落门禁写错会同时影响
  `advance` 与 `step-check`——这是刻意的：两份判断不应该分叉。

## 被否决的方案

- **在 `step_check.py` 里再写一张按工作流分支的步骤表**：等于把两份事实源换个位置，还会漂移。
- **把步骤表放进 `model-lab.yaml`**：清单是模型契约，步骤是方法学，混在一起会让每个工作区复制一份方法学。
- **让 `step_check` 直接解析 YAML**（不经过 `step_plan`）：核对器会二次实现段落与前沿语义，与 `lifecycle` 分叉。
- **按状态硬编码前沿**：维护工作流 `draft` 没有独立设计步、`released` 没有门禁，硬编码必然错。
