# GPU 目标的本地打包通道

状态：已接受（2026-10-14）

## 背景与决定

ADR 0003 已经确定"CPU、GPU 和 Chronos 部署共享同一套验证、打包、发布编排和结果契约，
目标环境差异由独立适配器承载"，`target.runtime` 也早已能表达 GPU 的算力、显存、CUDA 与
框架版本，`model_lab/decisions.py`、`model_lab/manifest.py` 与 `model_lab/runtime_contract.py`
的目标无关部分同样按这份契约工作。但打包这一步没有跟上：

- `model_lab/bundle_build.py` 的入口守卫是
  `if asset.summary.target != "cpu-iot" or asset.environment_requirements is None:`
  → `raise BundleBuildError("unsupported_target", "bundle-build currently supports CPU-IoT models with a target environment")`，
  即 GPU 目标**没有任何本地打包通道**。
- 后果是一个 GPU 模型可以走到 `validated`，却必然在 `validated → releasable` 的
  `mlflow-bundle-valid` 上失败，因为该门禁要求的六件套只能由 `bundle-build` 生成。
  这条缺口在 `models/_drafts/wwtp-world-model-mvp` 上被实际撞到。

同时有一条 ADR 0006 的既有边界必须尊重：制品摘要在清单中**只起登记作用，校验从不把 URI
解析到本地文件**，并且"构建流程自行生成服务包内的制品，不读取模型目录下的制品文件"。
GPU 权重恰恰是构建流程**无法自行生成**的东西，所以 GPU 分支必须为"从哪读权重"补一条
新契约，而不能靠解析清单 URI 绕过去。

决定：为 `bundle-build` 增加 GPU 分支，作为 ADR 0003"公共部署内核"在打包环节的补齐。

1. **`bundle-build` 接受 `cpu-iot` 与 `gpu` 两种目标**（`_SUPPORTED_BUNDLE_TARGETS`）。
   GPU 目标还要求 `target.runtime.accelerator == "gpu"`，否则报 `unsupported_target`。
   `chronos` 仍明确不支持——它没有可校验的制品契约，不猜。
2. **GPU 的构建输入是模型工作区内的 `release-bundle/service/artifacts/`，且它必须恰好
   放着清单声明的那些制品。** 多一个或少一个都报 `artifact_staging_mismatch`。
   这条约定同时满足三个约束：仓库安全策略（`model_lab/security_audit.py`）只允许权重落在
   `release-bundle/service/artifacts/<file>`；清单 URI 不被解析成文件系统路径（ADR 0006）；
   构建输入与目标主机无关，Windows 与 Linux 上同一份工作区产生同一份包。
   构建只从清单 URI 取**最后一段的文件名**作为声明名，用于和工作区里实际暂存的文件对账。
3. **构建把每个制品按文件名复制进服务包的 `artifacts/` 下**，与 `artifacts/model.py` 同目录。
   这样 `model_lab_service_runtime.SourceModel` 用 `runpy.run_path` 加载打包源码时，
   `Path(__file__).resolve().parent` 就是包内 `artifacts/`，打包源码按相对路径即可找到权重，
   **不需要给平台新增任何契约或环境变量**。
4. **恰好只放着声明制品的 `release-bundle/service/` 视为构建前暂存目录，而不是既有包。**
   构建先把暂存目录改名挪开、再把校验通过的 staged bundle 就位、最后删除挪开的目录；
   换入失败则把暂存目录放回。任何其它已存在的目录仍然照旧报 `bundle_exists`——
   "不覆盖既有包"这条不放松。
5. **`verify_mlflow_bundle` 增加一条只对 GPU 生效的检查**：清单里每个制品都必须在
   `bundle/artifacts/<声明文件名>` 存在且为普通文件，否则报 `missing_gpu_bundle_artifact`。
   该检查以 `runtime.accelerator == "gpu"` 为开关，且**不比对清单登记的 sha256**（ADR 0006）。
   既有 9 个在役模型全部是 `cpu-iot`、且制品 URI 一律用 `artifact://`，因此不受影响。

非目标：远端 GPU 上传与在线验收。按 ADR 0016，发布适配器只覆盖"具备在线验收收据的
CPU-IoT 测点模型"，GPU 目标的远端发布仍明确不支持。本 ADR 只打通**本地**打包，
`releasable` 的含义是"本地打包 + 静态校验通过"，不等于"已上传/已上线"。

## 后果

- 第一个 GPU 目标模型（`models/_drafts/wwtp-world-model-mvp`）得以走到 `releasable`，
  `mlflow-bundle-valid` 由 BLOCK 变为 PASS。
- **构建必须在声明目标平台上执行。** `check_build_environment` 会把
  `build_platform_mismatch` 记为硬 issue，`bundle-build --apply` 因此拒绝在
  Windows 控制面上构建 `linux/x86_64` 目标的包；生命周期门禁则把它降为 ADVISORY，
  允许在错配主机上推进设计。两者分工是刻意的：**设计可以在 Windows 上推进，
  最终生产实包必须在目标平台重建。**
- **权重受工作区 10 MB 硬限约束。** `security_audit.scan_workspace_tree` 对每个工作区文件
  判 `workspace_file_too_large`（`_MAX_HISTORY_BLOB_BYTES = 10_000_000`），
  `release-bundle/service/artifacts/` 下的权重不例外。因此本通道当前只支持
  **小于 10 MB** 的 GPU 制品；更大的权重需要外部暂存 + 策略变更，或改走
  `artifact://` 先上传的路径。这是本 ADR 的诚实限制，不是待办。
- 暂存目录会被构建消费掉（被服务包取代），因此**重建需要先删掉上一个包**。
  这与既有"不覆盖既有包"的行为一致，报错仍是 `bundle_exists`。
- 本改动目前只落在 `learn-model` 仓库。`learn-model-framework` 已与 `learn-model` 分叉
  （两者 `bundle_build.py` 内容不同），同步是独立动作，不在本 ADR 范围内。
