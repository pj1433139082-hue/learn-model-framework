# 模型模板必须通过脚手架实例化

## 决策

模型模板是模型实验室体系内部维护的版本化蓝本，不是供使用者手工复制的示例目录。新模型必须通过模型脚手架实例化；脚手架在写入前生成变更计划，只有显式应用后才在 `models/_drafts/<model-id>/` 创建模型工作区。模型工作区承载 draft、specified、built、validated 和 releasable 状态，不得因为文件齐全、验证通过或形成试运行计划而被视为 released。

`models/` 的在役层保持 released-only：除 `_drafts/`、目录说明文件及明确的仓库保留项外，其直接模型子目录只能保存已经发布并具备发布快照的模型资产。未来只有真实发布成功、加载与推理核验通过并形成不可变发布快照后，模型工作区才可提升到在役层；提升必须由公共入口编排，不能靠手工移动目录。

## 兼容边界

- 当前八个在役模型继续保留在现有 `models/01_...` 至 `models/08_...` 目录，不移动、不改名、不重新套用模板，也不因本决策产生隐含行为变化。
- `model.yaml` 继续是模型身份、契约、状态、版本和追溯信息的唯一事实源；模板生成的说明文档不得复制这些事实形成第二主档。
- 模型制品仍与源码分离。脚手架只登记制品 URI、摘要和兼容信息，不把权重、原始数据、长期凭据或原生运行库复制进普通 Git 历史。
- 公共 Interface 收敛为 `new`、`status` 和 `advance`。`new` 负责规划或实例化模型工作区，`status` 只读报告当前状态与下一准入门禁，`advance` 仅在门禁通过后单步推进本地生命周期。
- 真实远端发布后端仍然禁用。当前 `advance` 最多推进到 releasable；任何到 released 的请求都必须安全停止，不能调用旧 deploy 脚本绕过发布授权与安全评审。

## 后果

模板演进、路径规则、默认文件和检查逻辑集中在模型脚手架中，调用者只需学习三个公共入口。代价是模板文件不能被当作普通样例自由复制；需要新增目标差异时，应扩展内部目标适配器和模板配置，而不是复制出另一套流程。
