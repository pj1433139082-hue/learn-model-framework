# 0043 制品判定与快照身份收敛

- 状态：已接受
- 日期：2026-10-17

## 背景

两个「只有一个答案」的问题，曾经在多个模块里各答一遍。

**制品判定（#55）**：「哪一个制品是这个模型的服务制品」在 `archival`、`company_publish`、
`online_acceptance`、`workflow_state` 里各扫一遍 `artifacts` 找 `kind == "mlflow-pyfunc"`。四份实现
的"零件/多件"处理互不相同，同一份畸形清单在不同入口会得到不同错误码，甚至只在真正发布时才暴露。

**快照身份（#57）**：清单的 `platform` 块被至少三处判定——`asset_check._archive_status_issues`
（记录层错误码）、`asset_validation._historical_snapshot_issues`（历史快照错误码）、
`catalog._identity_values` + `_historical_platform_identities`（目录去重键）。三处的松紧、路径、
错误码都不一样；`catalog` 还要从 `ValidationCheck.details` 里把快照身份**反解成字符串**
（`f"{provider}:{experiment}"`、`run_id != "pending-archive"`）再重新拼装。任何一侧加一个字段、
改一个词表，另一侧只会在下次跑门禁时才以 `*_mismatch` 的形式暴露。

上一张卡（ADR 0032）已经把归档状态收敛到 `archive_state`、把快照的「写」与「检」收敛到
`snapshot_payload`，并明确把身份取值列为**范围外**；本 ADR 接手那部分，同时把 #55 的制品判定
纳入同一条收敛线：**判定与取值只留一份，消费者读类型化结果，而不是各自重算**。

写快照的路径当时还有一个结构性问题：`archival` 写完 `releases/<version>.yaml` 之后会做一次全量
`validate_manifest` 并在失败时回滚，但「写出来的东西是否等于校验器期望的东西」这件事，只有等到
**下一次跑门禁**或下一次别的原因触发全量校验时才会被证明。接口本身允许产出自己的校验器会拒绝的
快照，等于把漂移制造成接口缺陷，而不是使用者错误。

## 决策

1. **制品判定只有 `service_artifact` 一处**（`model_lab/manifest.py`）：输入清单、输出
   `ArtifactReference`（name/kind/uri/sha256/archive_status），`SERVICE_ARTIFACT_KIND = "mlflow-pyfunc"`
   只出现一次；四个消费者都读它。零件/多件不是各入口自定义的行为，而由 `require_unique=True` 统一抛
   `ManifestError("service_artifact_missing" / "service_artifact_ambiguous")`，归档路径再翻成
   `ArchiveError("archive_service_artifact_invalid")`。
2. **快照身份是一个类型化值** `PlatformIdentity`（`model_lab/asset_validation.py`，frozen dataclass）：
   字段 `path / provider / experiment / run_id / deployment_status / artifact_digests`；派生属性
   `run_pending`、`deployment_pending`、`pending`（三者同源）、`platform_key`（`provider:experiment`）、
   `run_key`（已解析时才 `provider:run`，`pending-archive` 时为 `None`）。归档状态不再另推导一遍：
   `archive_state` 的 `platform_pending` 直接读 `identity.pending`。
3. **读取器是纯函数** `platform_identity(document, *, path="")`：只读声明、只做类型收窄、不校验、不猜
   字段（非字符串一律读成 `None`），因此自然得到三态——正常已解析、缺字段（`None` 而非伪造值）、
   `pending-archive`（保留字面标记、`run_key` 为 `None`）。`artifact_digests` 取**记录登记的全部**
   SHA-256，而不是"服务制品摘要"：哪一件是服务制品是决策 1 的判定，位于入口层，下层不能也不该重做。
4. **历史快照身份只有一个回放入口** `snapshot_identities(document, manifest_path)`：按 `release.history`
   逐条装载快照文件，跳过无法解析的引用，返回 `PlatformIdentity` 元组。校验报告与资产目录消费同一份
   结果，不再有人从报告的 `details` 里二次拼装。
5. **写快照与查快照共用同一投影，报告只承载类型化值**：`archival._render_snapshot` 与
   `asset_validation._snapshot_issues` 都调用 `snapshot_payload`；`archival` 刻意以模块属性
   `_asset_validation.snapshot_payload` 晚绑定调用，使一次 monkeypatch 能同时改变写入与校验两侧
   （测试的"生产者-消费者矩阵"就是靠这一点证明同源）。`historical_release_snapshots` 检查的
   `snapshots` 从字符串字典改为 `PlatformIdentity.as_dict()`：`path / provider / experiment / run_id /
   count` 字段名不变，新增 `deployment_status / pending / platform_id / run_key / artifact_digests`；
   `as_dict()` 只产出 JSON 标量（`cli.py` 的 `json.dumps` 没有 `default=`，放 dataclass 会直接崩）。
6. **写入即校验，且必须在写入路径上**：`archival.archive_workspace` 写完清单与快照后立即用同一次
   投影调用做全量校验，不通过按既有回滚语义恢复工作区并抛 `ArchiveError("archive_validation_failed")`。
   只靠门禁不够，因为门禁是**事后**的：它发现漂移时文件已经写入、可能已被引用、可能已经进了发布
   预览；而且"接口能写出自己的校验器会拒绝的快照"这件事本身就是接口缺陷，门禁只是在替接口背锅。
   把校验放在写入路径上，"写入成功"从此蕴含"这份快照与清单自洽"，门禁只剩下复核外部事实
   （目录漂移、git 历史、草稿清单）的职责。
7. **目录层去字符串化，依赖方向钉死**：`catalog._identity_values` 读 `platform_identity(document)`，
   `_historical_platform_identities` 读 `snapshot_identities`，`_catalog_entry` 不再拼
   `f"{platform['provider']}:{platform['experiment']}"`；`details["snapshots"]`、
   `run_id != "pending-archive"` 这两类字符串手术在 `catalog.py` 内 grep 归零。`PlatformIdentity` /
   `platform_identity` / `snapshot_identities` 归 `asset_validation`，经 `asset_check` 再导出给
   `manifest`——沿用 ADR 0042 的 `check_vocabulary ← asset_validation / point_serving ← asset_check ←
   manifest`，`manifest` 不得直接 import `asset_validation`（`ValidationLayeringTests` 静态检查会红）。

## 后果

- 契约变化（`validate` / `release-gate` 的 JSON）：`historical_release_snapshots.snapshots[]` 由字符串
  字典变为结构化身份，字段名只增不改。对 01/09 的实测差异恰好是新增的
  `deployment_status / pending / platform_id / run_key / artifact_digests`，`issues`、`valid`、
  `release_snapshot`、`behavior_baseline` 逐字不变。
- 判定不再有第二份：`_historical_snapshot_issues`、`_archive_status_issues`、`archive_state`、
  `catalog` 四处对同一份清单给出同一结论；畸形快照的四个入口（库 `validate_manifest`、库
  `build_catalog`、CLI `validate`、CLI `catalog`）现在报同一个错误码。
- 兼容性：11 份既有快照全部继续 PASS。当前快照用严格键集差集比对（`snapshot_payload` 投影），
  历史快照用逐身份字段校验——后者是刻意的，`template-era`（v1，无 `target`/`contract`、单数
  `artifact` 无 `sha256`）形状必须继续可读；两种松紧的差异被 ADR 与测试同时钉住。
- 代价：多一个类型与两个读取器；报告里每份历史快照多 5 个字段；`archival` 对 `snapshot_payload`
  的调用从直接导入改成模块属性（晚绑定）——这层间接是"一次补丁同时影响写与查"的测试抓手，
  代码里有注释指向本 ADR，不能随手改回静态导入。

## 被否决的方案

- **把 `platform_identity` 放进 `manifest`（入口层）**：`asset_validation` 与 `asset_check` 不允许 import
  入口层，否则要么函数内 import 再造循环，要么把身份判定留在最上层、所有下层继续重算。经
  `asset_check` re-export 是唯一不破坏依赖方向的位置。
- **单开 `model_lab/ids.py` 收敛身份形状（T8 计划）**：身份不只是形状——「是否仍待归档」是身份语义，
  与 `pending-archive` 词表、`archive_state` 同源；本卡先在 `asset_validation` 收敛，`ids` 的谓词
  收敛留给 T8 评估，避免把语义拆到两个模块。
- **`catalog` 继续从 `details` 读结构化字典，只是去掉字符串拼接**：报告的 `details` 是校验产物，
  只覆盖"已通过校验的历史快照"，消费方仍得自己决定怎么装载、怎么拼 `platform_id`/`run_key`；报告
  字段一变 `catalog` 就崩。身份读取器是更稳的依赖。
- **让 `PlatformIdentity` 携带「服务制品摘要」**：服务制品判定属于入口层（`manifest.service_artifact`），
  下层不能调用；若在此重写一遍"哪件是服务制品"，就是让 #55 的收敛白做。改为登记的全部摘要，
  把"哪件服务"留给唯一判定。
- **写快照时只校验"能否反序列化/形状是否像 YAML"，语义留给门禁**：这正是缺陷本身——接口允许产出
  自己的校验器会拒绝的文件，使用者无从知道"写成功"是不是"写对了"。
- **历史快照也用严格键集差集（与当前快照同一把尺子）**：会把 11 份既有快照（尤其 v1 `template-era`）
  全部判死，兼容成本远高于收益；历史快照的契约本来就是身份字段级校验，缺平台记录仍会报
  `historical_release_snapshot_mismatch`（测试已固定）。
- **报告里继续保留字符串身份以兼容旧消费者**：新消费者会继续字符串手术，漂移只是换个地方发生；
  字段名不变的兼容性已经由 `as_dict()` 保证，没有必要保留字符串副本。
- **让 `catalog` 自己装载历史快照文件**：多一条装载/错误处理路径，还会绕过"清单校验不通过就不进目录"
  的短路——校验失败的资产会以目录条目形式出现，等于把错误当数据。

## 验证

- 定向：`python -m unittest tests.test_model_archive tests.test_archival tests.test_bundle_build`
  → `Ran 91 tests, OK (skipped=1)`；加 `tests.test_catalog` → `Ran 107 tests, OK (skipped=1)`。
- 新增 11 个用例（`tests/test_model_archive.py`）：`PlatformIdentityTests`（正常/缺字段/pending-archive
  三态、清单与当前快照同一身份、历史身份与报告逐项一致、入口层 re-export 同名）、
  `SnapshotSingleSourceTests`（给投影**加**一个键，写入产出与校验器同时看见；**删**一个键，两边同时
  看不见；写入产出与真实快照逐字相等且通过校验；v1 老快照固定样本继续 PASS）、
  `MalformedSnapshotConsumersTests`（缺键/多键/`artifact`+`artifacts` 混用 → 四个入口同报
  `release_snapshot_mismatch`；历史快照缺平台记录 → 四个入口同报 `historical_release_snapshot_mismatch`）。
- 全量：`python -m unittest discover -s tests` → `Ran 681 tests`，断言调用 2455 → 2509（+54）、
  用例 663 → 674（+11）；5 条失败全部归因并行会话的未跟踪文件（`models/_drafts/fan-efficiency-taierzhuang`
  下的越界数据文件与密钥形态文件，以及流程清单指向并行新建文档的断链），与本次改动无关。
- 四查：`release-gate` 的 8 项 check 与改动前逐项一致（`draft_inventory` 因上述并行文件仍 failed、
  issue 全部落在该目录内，属已知污染）；`validate` 01/09 的 `valid`、`issues`、`release_snapshot`、
  `behavior_baseline` 不变，差异只有上述新增身份字段；`status` 两份输出逐字节一致；`catalog`
  （9 个模型、`--check` 在役目录）输出逐字节一致。
